*** Phase 2: Key Discoveries

**** Armstrong: Process Isolation and "I Don't Care"
- Found Armstrong's core COP properties: isolation, async messaging, share-nothing, lightweight processes
- His thesis title: "Making reliable distributed systems in the presence of software errors"
- Key quote paraphrased: "Two processes on the same machine must be as independent as if they ran on physically separated machines"
- Isolation implies asynchronous messaging -- synchronous coupling destroys the isolation property
- "Let it crash" = processes do what they're supposed to or fail; they don't try to accommodate others' failures
- This maps directly to the user's "I don't care" principle: a communication module sends a message to an action module without knowing how the action is performed

**** Kay: Messaging, Not Inheritance
- Kay's OOP vision was inspired by biological cells: autonomous entities communicating via messages
- Core: "messaging, local retention and protection and hiding of state-process, and extreme late-binding"
- "The big idea is messaging" -- objects as biological cells that receive messages, process internally, emit results
- This is the exact three-role split viewed from the object/cell boundary: receive (communication), process (action), emit (data building for outbound messages)
- Kay explicitly said inheritance was NOT essential to OOP -- it was about message-driven computation

**** Ralf Westphal: Principle of Mutual Oblivion (PoMO) and IOSP
- CRITICAL FIND: Westphal formalized Kay's intuition into two principles:
  1. PoMO: "Two modules at the same level of abstraction should not know each other"
  2. IOSP: "Functions shall either only contain logic or they shall only call other functions"
- IOSP divides all functions into "operations" (contain logic, no calls) and "integrations" (call functions, no logic)
- This maps precisely to: communication = integration, action = operation, data building = operation
- Westphal explicitly traces this back to Alan Kay's biological cell analogy

**** Gary Bernhardt: Functional Core / Imperative Shell
- The "Boundaries" talk (SCNA 2012) proposes values (data) as the boundaries between components
- Shell = imperative, handles I/O and mutation; Core = functional, makes decisions
- Key insight: the shell has few paths but many dependencies; the core has many paths but no dependencies
- Maps to: communication (shell/routing) and action+data (core/logic)
- But notably, Bernhardt's model is two-role, not three-role -- it doesn't separate data building from action

**** Dave Thomas: Three-Module GenServer Split
- CRITICAL FIND: Dave Thomas explicitly proposed splitting Elixir GenServers into THREE modules:
  1. API module (client-facing functions) = communication
  2. Server module (GenServer callbacks, message routing) = communication/coordination
  3. Implementation module (actual business logic) = action
- Created a Component Library to generate these three modules from a single definition
- Elixir community debated this; conventional approach keeps all three in one file

**** Erlang OTP Behaviours
- OTP already embodies a two-level split: generic behaviour (gen_server) vs callback module
- The behaviour handles the "communication" concern (process lifecycle, message dispatch)
- The callback module handles "action" (what to do when messages arrive)
- State management (data building) is interleaved in callbacks -- no separate concern
- But the Elixir community's "thin GenServer" advice pushes toward extracting action into pure-function modules

**** CQRS and CQS
- Bertrand Meyer's CQS: every method either changes state (command) or returns data (query), never both
- CQRS extends this to system level: separate read models from write models
- The user's "CQRS-like directionality" maps well: each module (except communication) should only act OR respond
- Multiple action modules within one responsibility = the module acts in "multiple directions" = separate command-side and query-side actions

**** Clean Architecture / Hexagonal Architecture
- Hexagonal: inner hexagon (domain/action) knows nothing about outer hexagon (adapters/communication)
- Clean Architecture concentric layers: Entities, Use Cases, Interface Adapters, Frameworks
- Data mappers/DTOs live at the boundary between layers -- this IS the data building concern
- Both architectures separate "how we talk to the world" from "what we do" but treat data shaping as part of the adapter/interface layer

**** Builder/DTO/Factory Patterns
- GoF Builder pattern: "Separate the construction of a complex object from its representation"
- DTO pattern: lightweight data structures with no business logic, used at boundaries
- Factory pattern: centralized object creation
- All three support the idea that data construction is a distinct concern worth separating

*** Phase 3: Codebase Example Analysis

Examined ~/src/compiler/macro/macros/videoOutput/ as the real-world example.

**** Structure observed:
- =index.ts= (top-level): COMMUNICATION -- routes to outputVideo or outputImage based on target type
- =outputVideo/index.ts=: ACTION/ORCHESTRATION -- the main action function that coordinates the video output macro
- =outputVideo/buildOutputNode.ts=: DATA BUILDING -- constructs ExpandedNode objects for the encode-video and output nodes
- =outputVideo/buildVideoData.ts=: DATA BUILDING -- constructs the VideoData structure from segments
- =outputVideo/segments/index.ts=: DATA BUILDING -- constructs Segment objects, validates, combines
- =outputVideo/connectFrameNodes.ts=: COMMUNICATION/WIRING -- connects nodes in the graph via edges
- =outputVideo/initializeVideoLoop.ts=: MIXED (builds loop node + connects it)
- =outputVideo/connectTimelineData.ts=: COMMUNICATION/WIRING
- =common/connect.ts=: COMMUNICATION primitive -- the fundamental =connectNodes= function that creates edges

**** Observations:
1. The three roles are clearly present but not rigidly separated
2. =build*= functions are pure data builders -- they construct and return ExpandedNode objects
3. =connect*= functions are communication wiring -- they create edges between nodes
4. The =outputVideo/index.ts= orchestrator interleaves calls to both build and connect functions
5. Some files mix roles (e.g., initializeVideoLoop builds a node AND connects it)
6. The =connectNodes= utility is the ultimate "I don't care" example: it creates an edge from any node to any node without knowing what either does

*** Phase 4: Synthesis -- The Three-Role Pattern

**** No exact prior art found
No established pattern in the literature uses exactly this three-role decomposition (communication / action / data building) at the module level. However, the pattern is a natural synthesis of several well-established ideas.

**** Closest relatives:
1. Westphal's IOSP: integration (communication) vs operation (action + data building)
2. Bernhardt's FCIS: shell (communication) vs core (action + data building)
3. Dave Thomas's three-module GenServer: API + Server + Implementation
4. OTP behaviour split: generic behaviour + callback module (but missing explicit data building)
5. Clean/Hexagonal: adapters (communication) + domain (action) + mappers/DTOs (data building)
6. Builder pattern: explicit separation of construction from use

**** What makes this pattern distinct:
- It operates WITHIN a single module responsibility, not between architectural layers
- It is NOT about external boundaries (MVC, hexagonal) but about internal decomposition
- Data building is elevated to a first-class concern equal to action, not treated as a utility
- The "I don't care" principle is enforced between siblings, not between layers
- Directionality (CQRS-like) applies per sub-module, not per system boundary
