* Research: Denote System Applicability for General Project Knowledge DB

** Recommendation

The answer is *yes, with differentiation*. The denote system can serve
as a general project knowledge DB, but the two primary use cases (code
project facts vs. creative project knowledge graphs) have fundamentally
different requirements and should be addressed separately.

*** For Code Projects: Lightweight Notes Directory

Goal 1 (code-undiscoverable facts) and Goal 3 (context optimization)
are served by a simple extension:

- A =notes/= directory alongside =designs/= with denote-named org
  files containing atomic facts
- Same front matter schema as design artifacts (=#+title:=,
  =#+filetags:=, =#+identifier:=, =#+signature:=) plus arbitrary
  =#+key:= fields as needed
- New type tag: =:fact:= for atomic knowledge entries
- Queryable via =denote-query --dir notes/= or =--dirs designs/,notes/=
- No templates — notes are chaotic by nature. Denote front matter
  provides the minimal structure; domain-specific fields are organic.
- Claude discovers facts during code investigation and persists them;
  human adds facts that don't fit any design doc
- Convergence gate extended to also scan =notes/= (via =--dirs=)
- Lint runs at every flow init across all directories

*Scale:* ~50-100 facts for a typical project. Full-corpus read is
~5-10K tokens — trivial for the 1M context window. No optimization
needed beyond =denote-query=.

*Boundary with Claude Code memory:* Memory stores behavioral
directives ("use E2E tests, not unit tests"). Knowledge stores
factual content ("the operation pool cap is 40"). Memory is
auto-loaded every session. Knowledge is queried on demand.

*Abandonment risk:* Low. Adding 4 lines of front matter to a fact
file is minimal overhead. =denote-query= already exists.

*** For Creative Projects (TTRPG, Worldbuilding): Separate Design

Goal 2 (genuine knowledge graph) requires more infrastructure and is
tracked as a *separate design artifact*: "creative project knowledge
graph." It shares =denote-query= tooling but differs in everything else.

Key characteristics (to be designed separately):

- Same =notes/= directory with subdirectories by entity type
  (=characters/=, =atlas/=, =organizations/=, =lore/=, =campaigns/=)
- Extended front matter with domain-specific =#+key:= fields
  (=#+faction:=, =#+location:=, =#+aliases:=) — extracted by the
  extended AWK scanner
- No templates — notes are chaotic. Denote front matter is the only
  prescribed structure; domain-specific fields are organic per project
- Structure notes (tagged =:structure:=) for compilation ordering
- Cross-linking via =[[denote:ID][Title]]= identifier-based links
- New =denote-query= subcommands: =table=, =orphans=, =recent=,
  =count-by=, =field= (arbitrary field query)

*Authorship model:* Human-primary for lore and setting content. Claude
reads, queries, compiles, and maintains cross-reference integrity.

*Compilation:* Claude reads a structure note, reads referenced entity
notes, weaves into a final document. Structure note = table of contents.

*Abandonment risk:* Medium. Entity templates and structure notes
require ongoing discipline. The Karpathy insight applies: AI should
handle bookkeeping (orphan detection, stale metadata, missing links)
while humans handle curation.

*** For Context Optimization: Already Solved at Current Scale

Goal 3 is a non-problem at projected scale. The constraint analysis
shows:

- 500 atomic notes: ~50-100K tokens for full content read (5-10% of
  the 1M context window)
- =denote-query= already provides two-stage filtering (metadata →
  content) that reduces token usage by 90%+ for targeted queries
- Compiled views for prompt caching are not needed — the per-file
  overhead is negligible when reading via =denote-query= batch
  extraction

Compiled views become relevant only at 1000+ notes with large
content per note. This is speculative and deferred.

** Findings

*** Zettelkasten Principles (applicable to both use cases)

From the Zettelkasten tradition and modern implementations:

- *Atomic notes:* Each note captures one idea/fact. This scales.
- *Structure notes:* Index notes that organize related content into
  a navigable structure. Essential for compilation and narrative flow.
- *Explicit links carry meaning search cannot replicate:*
  "Full-text search alone provides not enough material" (zettelkasten.de)
- *Failure modes:* Collector's fallacy (gathering without connecting),
  orphan notes, stale knowledge, over-reliance on search.
- Tags for weak grouping, links for strong connections.

*** Karpathy's LLM Wiki Model

Three-layer architecture: raw sources → AI-maintained wiki → schema.
Three operations: ingest (add knowledge), query (search+synthesize),
lint (detect staleness, contradictions, orphans).

Key insight: *AI handles bookkeeping, humans handle curation.* Schema
quality determines system quality. Drift (stale cross-references) is
the primary failure mode.

Applicable to both use cases: lint operations (orphan detection, stale
metadata flagging) are valuable regardless of KB type.

*** Memex/Mimex Influence

Vannevar Bush's 1945 memex concept: associative trails through a
knowledge corpus, not hierarchical classification. Modern relevance:
knowledge should be navigable by association (links, tags, related
concepts), not by rigid folders alone.

Applicable principle: directories for *type* (NPC, location, design),
tags for *topic* (faction-X, region-Y). This matches the Obsidian
community's converged pattern.

*** Obsidian Patterns (for creative KB)

Detailed in =obsidian-patterns.org=. Key transferable patterns:

- *Entity templates:* Standardized front matter per entity type (NPC:
  race, class, faction, location, status; Location: region, population,
  government). Directly translatable to org front matter.
- *Embedded queries:* Dataview queries inside notes that show related
  entities. In denote: =#+begin_src shell= blocks calling =denote-query=.
- *MOCs (Maps of Content):* Structure notes that curate navigation.
  In denote: structure notes tagged =:structure:=.
- *Session → entity workflow:* Write session recap, update entity
  metadata, let queries surface current world state.
- *Pain points:* Orphan notes, naming drift, stale metadata, link rot.
  All mitigatable with =denote-query lint= and =denote-query orphans=.
- *Graph View is decorative:* Community consensus is that backlinks and
  search are more useful than visual graph navigation.

Denote's filename convention is *more* AI-friendly than Obsidian's
approach: metadata visible at the filesystem level without opening
files.

*** Existing Systems Audit

Three existing knowledge systems are fragmented:

| System      | Purpose            | Query mechanism     | Scope          |
|-------------+--------------------+---------------------+----------------|
| Memory      | Behavioral         | Auto-loaded         | Per-project    |
| Denote      | Design lifecycle   | denote-query script | Per-project    |
| CLAUDE.md   | Project setup      | Always in context   | Per-project    |

The knowledge DB fills the gap: *factual content about the system
or domain that doesn't fit design artifacts or behavioral memory.*

*** Constraints

*Hard:* filesystem-only tools, no Emacs/SQLite, AWK scanner needs
schema extension for domain-specific fields, cross-directory
=[[file:]]= links require =../= prefixes, no file locking.

*Soft:* grep scales to ~2000-5000 notes, type/heading vocabularies
need extension, no ordering mechanism (use structure notes), authorship
tracking desirable.

*Anti-constraints:* 500 notes fits grep performance, full-corpus reads
fit context window, two-stage query pattern works as-is, separate
directories don't prevent cross-linking.

** Decision

All open questions resolved. Decisions below.

*** Directory naming
=notes/= — consistent across all project types. Both code projects and
creative projects use =<project>/notes/= for knowledge entries.

*** Multi-directory queries
=denote-query= gets a =--dirs= flag accepting comma-separated paths
(e.g., =--dirs designs/,notes/=). This enables scoped queries like
"search designs and LLM wiki but not raw notes." The existing =--dir=
flag (single directory) is preserved for backward compatibility.

*** AWK scanner extension
The AWK scanner is extended to extract arbitrary =#+key:= fields, not
just the hardcoded 5. This enables domain-specific queries (e.g.,
=denote-query field faction "Thieves Guild"=) without packing
everything into filetags.

*** Lint trigger
Lint runs at every flow init, alongside the convergence gate. This
catches heading drift early. Latency is negligible (<20ms at 200 files).

*** Memory ↔ knowledge boundary
No automatic migration. Memory entries stay in Claude Code's memory
system. If migration is needed, the user requests it explicitly.
Boundary rule: behavioral directives → memory; factual knowledge →
=notes/=.

*** Creative KB scope
The TTRPG/creative knowledge graph is a separate design artifact from
the code-project knowledge directory. They share =denote-query= tooling
but differ in directory structure, metadata schema, authorship model,
and query patterns. Tracked as a separate design: "creative project
knowledge graph."

*** No templates
The knowledge system does not prescribe entity templates. Notes are
chaotic by nature. The denote front matter (=#+title:=, =#+filetags:=,
=#+identifier:=) provides the minimal structure; domain-specific fields
(=#+faction:=, =#+location:=) are added organically per project.

** Question
Can the denote/denote-query system be extended to serve as a general
project knowledge DB — covering code-undiscoverable facts, genuine
knowledge graph handling (non-tree cross-linked documents), and Claude
context optimization?

** Context
The denote metadata system (=DENOTE.md= + =denote-query= script) was
designed for design artifact management (research, design, implementation
lifecycle). The user wants to explore whether the same conventions and
tooling can serve broader knowledge management needs across different
project types, including non-code projects (e.g., TTRPG settings).

Key influences: Zettelkasten (networked notes), Mimex (as inspiration,
not strict methodology).

** In Scope
- Goal 1: Code-undiscoverable facts — facts about a system that don't
  fit any design or research doc but should be discoverable. Both
  user-known facts and Claude-discovered facts from deep code/doc
  investigation. "Memorize once for further optimization."
- Goal 2: Genuine knowledge graph — cross-linked, non-tree documents.
  Use case: TTRPG setting (gods, religions, adventures, NPCs, locations)
  where documents are entangled. Hybrid maintenance (manual + Claude).
  Output: final descriptive documents and web pages (e.g., "all gods
  and religions in my setting", "campaign adventure progression").
  Sub-questions:
  - Should knowledge DB have its own directory (=<project>/knowledge/=)
    separate from =<project>/designs/=?
  - Can the existing designs system be extended for seamless knowledge/
    designs interlinking while keeping =denote-query= folder-scoped?
- Goal 3: Claude context optimization — by introducing a proper file-
  based knowledge DB with =denote-query=, can Claude's context window
  usage be improved? Inspired by Karpathy's LLM OS/wiki concept
  (https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f).
  Key question: should an "LLM wiki" be the same system as a hybrid
  human+AI knowledge DB, or should they be separate?

** Out of Scope
- Implementation changes to =denote-query= script (that's a subsequent
  design task)
- Specific TTRPG content or setting design
- Code-as-documentation reviewer (tracked separately in
  =code-as-documentation.org=)

** Evaluation Criteria
1. Generality — works for code projects AND non-code projects
2. Denote compatibility — reuses existing conventions and tooling
3. Graph expressiveness — handles genuine cross-linking, not just trees
4. Hybrid maintenance — both human and Claude can create/edit/query
5. Context efficiency — improves Claude's token usage vs. raw file reads
6. Separation of concerns — knowledge DB doesn't pollute design artifacts
