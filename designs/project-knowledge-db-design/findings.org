** 1. Zettelkasten for Project Knowledge (not just personal notes)

*** 1a. Core Zettelkasten Note Types

The Zettelkasten method defines several note categories that map
directly to project knowledge needs:

- *Content Notes (Zettels)*: Atomic units capturing a single topic
  with a unique identifier. The principle of atomicity is central ---
  each note addresses one idea.

- *Structure Notes*: Middle-layer organizational notes that connect
  related content notes. They provide navigational context --- like a
  table of contents for a topic cluster. These are not mere indexes
  but carry their own argumentative structure.

- *Main Structure Notes (Hub Notes)*: Top-level entry points into
  major topic areas. These use special tags and serve as the "front
  doors" to knowledge clusters.

- *Literature/Reading Notes*: Extracted information from external
  sources, not yet fully processed into content notes. These preserve
  provenance.

- *Buffer Notes*: Temporary collection points for incoming
  information awaiting integration.

*** 1b. Cross-Linking Patterns

The Zettelkasten method explicitly rejects tree-based organization in
favor of a web:

- *Direct links*: Point-to-point connections between notes. The
  zettelkasten.de overview emphasizes that full-text search alone is
  insufficient --- explicit links carry semantic meaning that search
  cannot replicate.

- *Note sequences*: Related notes connected in meaningful order,
  forming argumentative chains.

- *Tag-based clustering*: Tags provide weak grouping without
  enforcing hierarchy. Multiple tags per note enable cross-cutting
  categorization.

- *Bidirectional discovery*: Tools like Obsidian and org-roam
  automatically surface backlinks, enabling discovery of unexpected
  connections.

*** 1c. Failure Modes

- *Collector's Fallacy*: Gathering information without actively
  synthesizing it. The zettelkasten.de site identifies this as the
  primary failure mode --- accumulating notes without connecting or
  reworking them.

- *Orphan notes*: Notes that are created but never linked to anything
  else. These represent dead knowledge.

- *Stale knowledge*: Notes that were accurate when written but have
  not been updated as the domain evolved. No Zettelkasten tool
  provides automatic staleness detection.

- *Over-reliance on search*: Using search as a substitute for
  deliberate connection-making, leading to a flat collection rather
  than a knowledge web.

- *Rigid hierarchy*: Imposing folder-based categorization on notes
  defeats the web-like nature of the system. Tags and links should be
  primary; folders should be optional.

*** 1d. Tool Comparison for Project KB

| Tool      | Storage      | Linking          | Graph View | AI Support | Team Use    |
|-----------+--------------+------------------+------------+------------+-------------|
| Obsidian  | Markdown     | [[wikilinks]]    | Built-in   | Plugins    | Vault sync  |
| Logseq    | Markdown/Org | [[wikilinks]]    | Built-in   | Minimal    | Git-based   |
| org-roam  | Org-mode     | id: links + DB   | Built-in   | None       | Git-based   |
| Denote    | Org/Md/Txt   | file: links      | None       | None       | Git-based   |
| nb        | Md/Org/LaTeX | [[wiki]] + IDs   | None       | None       | Notebooks   |

Key distinction: Obsidian and org-roam maintain a database/cache of
links for fast backlink computation. Denote deliberately avoids this,
relying on filesystem naming conventions and grep. This trades
features (no automatic backlink buffer) for simplicity (no database
to corrupt, no sync issues).

** 2. Memex / Mimex Concepts

*** 2a. Vannevar Bush's Original Memex (1945)

The Memex concept from "As We May Think" embodies several principles
directly relevant to this research:

- *Personal knowledge augmentation*: The device supplements individual
  memory by storing all books, records, and communications for rapid
  retrieval.

- *Associative trails*: Rather than rigid hierarchical indexing, users
  create pathways through materials that reflect conceptual connections.
  Bush described creating "a new linear sequence" across materials
  through "a chained sequence of links" with personal annotations.

- *Trail sharing*: Trails could be saved and shared with colleagues,
  allowing others to follow a researcher's reasoning. This is an early
  vision of collaborative knowledge trails.

- *Annotation as first-class*: Users add personal commentary to create
  interpretive layers over raw materials.

*** 2b. Modern Memex Influence

The Memex concept directly inspired:

- *Hypertext* (Ted Nelson, 1965): Explicitly referenced Bush's work.
- *The World Wide Web* (Berners-Lee, 1989): Reflected similar linking
  principles.
- *Microsoft MyLifeBits*: An attempt at comprehensive personal
  information capture.
- *DARPA Memex program*: Modern large-scale implementation.

*** 2c. Memex vs Zettelkasten

The two traditions address overlapping but distinct concerns:

| Aspect        | Memex                          | Zettelkasten                    |
|---------------+--------------------------------+---------------------------------|
| Unit          | Documents + annotations        | Atomic notes                    |
| Organization  | Associative trails             | Links + tags                    |
| Creation      | Curating & annotating sources  | Synthesizing & reformulating    |
| Emphasis      | Retrieval & navigation         | Thinking & connection-making    |
| Sharing       | Trail-sharing                  | Structure notes as entry points |

For a project knowledge DB, the Zettelkasten model (atomic, linked
notes) is more directly applicable than the Memex model (annotated
document trails). But the Memex insight about shareable trails maps
well to "structure notes" that curate a reading path through a topic.

** 3. Karpathy's LLM Wiki

*** 3a. Core Architecture

Karpathy proposes an architecture where LLMs incrementally build and
maintain a persistent wiki --- a structured, interlinked collection
of markdown files. This is perhaps the most directly relevant
external finding.

Three-layer architecture:
1. *Raw sources (immutable)*: Curated collection of articles, papers,
   documents. Never modified by the LLM.
2. *The wiki (LLM-maintained)*: Markdown files organized as summaries,
   entity pages, concept pages, cross-references. The LLM owns this
   layer.
3. *The schema (configuration)*: A document like CLAUDE.md that
   defines wiki structure, conventions, and workflows.

*** 3b. Three Core Operations

1. *Ingest*: When you add a source, the LLM reads it, extracts key
   information, and integrates it into the existing wiki --- updating
   entity pages, revising topic summaries. This is NOT mere indexing.

2. *Query*: Ask questions against the wiki. The LLM searches relevant
   pages and synthesizes answers with citations. Valuable findings can
   be filed back as new pages.

3. *Lint*: Periodically health-check the wiki for contradictions,
   stale claims, orphan pages, and missing cross-references. This
   directly addresses the Zettelkasten failure mode of stale knowledge.

*** 3c. Key Insight: Labor Division

Karpathy's fundamental insight: "The tedious part of maintaining a
knowledge base is not the reading or the thinking --- it's the
bookkeeping." Humans handle curation and analysis; LLMs handle the
maintenance burden that grows faster than human motivation.

This is directly applicable to the project knowledge DB question:
the system should be designed so Claude handles the bookkeeping
(cross-references, staleness detection, index maintenance) while
humans handle the knowledge curation.

*** 3d. Production Findings

From actual usage:

- *Schema is everything*: The configuration file (analogous to
  CLAUDE.md) evolved into the most important document. It disciplines
  the agent into systematic behavior.

- *Drift is the primary failure mode*: Under-updating cross-references
  leaves pages silently stale. Regular linting is non-optional.

- *Provenance matters*: Pages carry extraction provenance and staleness
  markers so consumers know what they're reading.

- *Size matters less than compression*: The compounding synthesis
  advantage emerges around hundreds of pages. Repeated reads can drop
  to 13-token references in deduplication systems.

*** 3e. Relationship to Claude Code Memory

Claude Code's current CLAUDE.md system is essentially a single-file
version of layer 3 (the schema). Karpathy's model suggests the
natural evolution is to add layers 1 (raw sources --- already exist
as code) and layer 2 (the wiki --- the proposed knowledge notes).

** 4. Knowledge Graphs for Creative Projects

*** 4a. Worldbuilding Knowledge Structure

LegendKeeper's architecture reveals the canonical entity types and
relationships in creative project knowledge:

- *Lore entities*: Characters, locations, organizations, concepts ---
  connected through auto-linked wiki pages.
- *Spatial entities*: Map-based entities with geographic relationships.
- *Temporal entities*: Timeline events, eras, lineages with parallel
  storyline tracking.
- *Relational entities*: Relationship boards visualizing faction webs,
  conspiracies, quest flows.

Key patterns:
- *Auto-linking*: Terms auto-link throughout wiki pages, creating
  emergent relationship networks without manual link maintenance.
- *Spatial-semantic binding*: Geographic and narrative knowledge are
  merged, not siloed.
- *Granular access control*: Hidden secrets enable selective
  revelation --- a pattern relevant to separating "player knowledge"
  from "GM knowledge."

*** 4b. Obsidian for Worldbuilding

Obsidian's graph view represents notes as nodes and links as edges,
with node size proportional to incoming link count. This provides
visual discovery of hub entities (heavily connected notes like major
locations or key NPCs) vs peripheral entities.

Worldbuilders commonly use:
- *Templated note types*: Separate templates for Character, Location,
  Faction, Event, etc., each with standardized frontmatter fields.
- *Dataview plugin*: SQL-like queries against note frontmatter,
  enabling "all characters in faction X" or "all events in era Y."
- *Tag hierarchies*: Nested tags like #faction/empire and
  #faction/rebel for cross-cutting categorization.
- *Canvas/Excalidraw*: Visual relationship mapping for complex webs.

*** 4c. Digital Gardens as Model

Maggie Appleton's digital garden concept provides a maturity model
for knowledge notes:

- *Seedlings*: Early-stage ideas, rough and incomplete.
- *Budding*: Partially developed, linked to some related notes.
- *Evergreen*: Well-developed, heavily cross-linked, regularly
  maintained.

This growth model maps to a project knowledge DB where notes
can have an explicit epistemic status (draft, reviewed, stale).

*** 4d. Gwern's Technical Approach

Gwern.net implements several patterns relevant to a file-based
knowledge system:

- *Filesystem-based tagging*: Files in =/doc/foo/bar/= automatically
  receive the =foo/bar= tag. This eliminates redundant metadata entry.

- *Semantic zoom*: Content organized at multiple depth levels ---
  headline, summary, full detail --- enabling readers to skim or dive.

- *Bidirectional backlinks with context*: Not just "what links here"
  but showing the exact context in which each link appears.

- *Neural network embeddings for similarity*: Suggesting related
  content based on semantic similarity, not just explicit links.

- *Local archiving against link rot*: Preemptively caching linked
  content.

** 5. AI + Knowledge Base Patterns

*** 5a. Current AI Coding Assistant Context Patterns

The landscape of AI coding context management shows convergent
evolution toward a layered approach:

| Tool            | Static Context                 | Dynamic Context            | Persistent KB |
|-----------------+--------------------------------+----------------------------+---------------|
| Claude Code     | CLAUDE.md (hierarchical)       | Conversation + tool use    | Memory files  |
| GitHub Copilot  | .github/copilot-instructions   | Current file + neighbors   | None          |
| Cursor          | .cursorrules + /docs/rules     | Session + selected files   | Skills        |
| Aider           | Conventions + repo map         | Chat + selected files      | Git history   |
| Goose           | MCP extensions                 | Session context            | Minimal       |

Key observation: all tools converge on a "static instructions file"
pattern (CLAUDE.md, .cursorrules, copilot-instructions.md) for
code-undiscoverable facts. None currently offer a structured,
multi-file knowledge base beyond this.

*** 5b. GitHub Copilot's Approach

GitHub Copilot's =.github/copilot-instructions.md= is the most
explicit formulation of the "code-undiscoverable facts" problem. Their
documentation recommends including:

1. High-level repository details (project summary, languages, frameworks)
2. Build and validation steps
3. Architecture overview with file locations
4. CI/validation pipeline documentation

Crucially, they instruct the agent to "trust the instructions and only
perform a search if the information in the instructions is incomplete
or found to be in error." This privileges curated knowledge over
dynamic discovery.

*** 5c. Mem0: Multi-Level AI Memory

Mem0 implements a three-tier memory architecture for AI agents:

1. *User Memory*: Long-term preferences and characteristics.
2. *Session Memory*: Context within individual conversations.
3. *Agent Memory*: State information for autonomous systems.

Their hybrid retrieval combines:
- Semantic search (vector embeddings)
- BM25 keyword matching
- Entity linking across memories
- Temporal reasoning (distinguishing current state from past events)

Their April 2026 algorithm achieves 92.5 on LoCoMo benchmarks with
single-pass extraction and additive-only memory (no overwrites).

*** 5d. Microsoft GraphRAG

GraphRAG transforms documents into structured knowledge graphs using
LLMs for entity extraction and relationship mapping. Key features:

- *Entity and relationship extraction*: LLMs identify entities and
  connections, building structured representations.
- *Community detection*: Graph analysis identifies clusters of related
  concepts for hierarchical understanding.
- *Multi-hop reasoning*: Graph structure enables reasoning across
  relationships that flat retrieval cannot.

This is expensive but demonstrates the value of explicit relationship
modeling over flat document retrieval.

*** 5e. Kotaemon: Document-Based Knowledge with Graphs

Kotaemon provides a hybrid RAG pipeline combining full-text and
vector-based retrieval with re-ranking. It offers GraphRAG
implementations (Nano GraphRAG, LightRAG) as alternatives to
Microsoft's approach, with multi-modal support and customizable
pipelines.

*** 5f. Aider's Repo Map: PageRank for Code

Aider's approach to project context is technically interesting: it
uses tree-sitter to extract code definitions, builds a graph of
definition-to-reference relationships, and applies PageRank to
determine what context to include. Files mentioned in chat get a 50x
personalization weight.

This is a purely code-discoverable approach and cannot handle the
"code-undiscoverable facts" problem. But the PageRank-based relevance
ranking is a pattern worth noting for knowledge note retrieval.

*** 5g. TIL (Today I Learned) Pattern

Josh Branchaud's TIL repository demonstrates a minimalist atomic note
pattern: ~1820 notes across 83 technology categories, each a single
markdown file capturing one discrete concept. The flat
category-per-directory structure is simple and scales well.

This pattern maps directly to a "project facts" collection: atomic
notes organized by topic, each addressing one undiscoverable fact.

*** 5h. Prompt Caching Implications

Anthropic's prompt caching system has direct implications for
knowledge DB design. Key patterns:

- *Static content first*: Place stable, reusable content at the
  prompt's beginning (system instructions, tool definitions,
  background knowledge).
- *Separate by change frequency*: Content that changes rarely should
  be cached separately from content that changes per-turn.
- *Minimum cacheable size*: For Claude Opus 4.6, the minimum is 4096
  tokens. Knowledge notes below this threshold cannot be cached
  individually; they must be bundled.

This means a knowledge DB should support "compiled views" that bundle
related notes into cacheable chunks of >=4096 tokens.

** 6. Cross-Cutting Synthesis

*** 6a. Convergent Patterns Across All Sources

1. *Atomic notes are universal*: Every successful knowledge system
   (Zettelkasten, TIL, LLM Wiki, worldbuilding tools) converges on
   atomic, single-topic notes as the fundamental unit.

2. *Links carry semantic weight*: Search alone is insufficient.
   Explicit links between notes encode relationships that cannot be
   discovered through content search.

3. *Structure notes are essential*: Hub/index/structure notes that
   curate pathways through atomic notes are necessary for navigation
   at scale. Without them, the knowledge web becomes unusable.

4. *Staleness is the killer*: The primary failure mode across all
   systems is stale, unmaintained notes. Karpathy's "lint" operation
   is the most explicit solution proposed.

5. *AI handles bookkeeping, humans handle curation*: The natural
   labor division is for AI to maintain cross-references, detect
   staleness, and compile views, while humans make knowledge
   decisions.

6. *File-based storage works*: Denote, TIL, digital gardens, and
   Karpathy's wiki all use plain files. No system surveyed requires
   a database for the knowledge itself (though some use databases
   for link caching).

*** 6b. Gaps in Current Approaches

1. *No tool combines file-based atomic notes with AI maintenance*:
   Karpathy describes this conceptually but there is no packaged
   implementation. This is the space the proposed system would
   occupy.

2. *Relationship types are underspecified*: Most Zettelkasten tools
   treat all links as equivalent. Worldbuilding tools distinguish
   relationship types (member-of, located-in, allied-with). A
   project KB may need typed relationships.

3. *Compiled views are rare*: The ability to generate a "gods
   document" or "faction overview" from atomic notes is mostly
   manual. LegendKeeper and Dataview provide some automation, but
   AI-driven compilation is unexplored.

4. *Context window optimization is ad hoc*: No knowledge system is
   designed with LLM context window constraints in mind. Prompt
   caching considerations (minimum sizes, change frequency
   separation) are not reflected in any note-taking tool's design.
