* Executive Summary

This report documents practical patterns used in Obsidian for project knowledge
bases, TTRPG/worldbuilding management, and AI-augmented note-taking. Each
pattern is assessed for transferability to an Emacs+Denote+denote-query stack.

The core finding: Obsidian's power comes from three pillars --- structured
metadata (YAML frontmatter), queryable databases (Dataview), and frictionless
linking ([[wikilinks]]). Denote already covers metadata and linking natively;
the gap is primarily in /dynamic embedded queries/ and /visual graph
navigation/. denote-query can fill most of the Dataview gap.

* 1. Obsidian for Project Knowledge Management

** 1.1 How People Organize Project Knowledge Bases

*** Folder Structures in Practice

The dominant organizational methods are PARA (Projects, Areas, Resources,
Archive), Zettelkasten (flat + links), and Johnny Decimal (numbered
hierarchies). In practice, experienced users converge on a hybrid: 5--10
top-level folders with minimal nesting, combined with rich links and tags.

A typical engineering/project KB vault:

#+begin_example
vault/
  raw/                    # Unprocessed captures, imports, clippings
  raw/processed/          # Staged for promotion to wiki
  wiki/
    sources/              # Immutable reference material (articles, PDFs)
    entities/             # Named things: tools, services, people, APIs
    concepts/             # Ideas, patterns, architectural decisions
    index/                # MOCs (Maps of Content) - curated entry points
    log/                  # Chronological entries, decision log
  journal/                # Daily/weekly notes
  crm/                    # People and relationship tracking
  agents.md               # AI agent configuration (conventions, workflows)
  index.md                # Root entry point
  log.md                  # Change log
#+end_example

Key insight: folders answer "where does this belong?" while tags answer "what is
this about?" The best vaults use folders for /type/ (NPC, location, session) and
tags for /topic/ (faction-X, region-Y, needs-review).

*** The Documentation vs. Notes Boundary

A critical architectural decision: raw sources are /immutable/ (never edited
after creation), while wiki pages are /living documents/ that synthesize and
cross-reference. This separation is especially important for AI integration:

- =raw/= :: staging area for captures, voice memos, clipboard pastes
- =sources/= :: immutable reference material (the "source of truth")
- =wiki/= :: model-written and human-edited synthesis pages
- =CLAUDE.md= or =AGENTS.md= :: operating rules for AI agents

The model reads from =raw/= and =sources/=, writes to =wiki/=, and follows
conventions defined in the agents file.

between having an idea and capturing it.

** 1.3 Maps of Content (MOCs)

MOCs are navigation notes --- curated lists of links around a theme, with
commentary explaining why each note was included and how they relate.

Key principles from experienced users:

- Do NOT create MOCs upfront. Let them emerge when 7--10 notes accumulate
  around a topic and become hard to find.
- MOCs are the "middle layer" between a single giant index (nobody updates) and
  a flat pile of notes (nobody navigates).
- Unlike folders, the same note can appear in multiple MOCs --- this is the core
  advantage over hierarchical organization.
- Each MOC link gets a phrase of commentary; the curation is what separates a
  MOC from a tag search.

Example MOC structure:

#+begin_example
# Authentication Systems MOC

## Core Concepts
- [[OAuth 2.0 Flow]] — the baseline protocol everything builds on
- [[JWT Token Structure]] — stateless auth, trade-offs vs sessions
- [[PKCE Extension]] — why SPAs need this over implicit flow

## Our Implementation
- [[Auth Service Architecture]] — how we wired MSAL + Express
- [[Token Refresh Strategy]] — the silent-refresh vs refresh-token decision
- [[2024-03 Auth Migration Notes]] — context for the Azure AD → Entra rename

## Open Questions
- [[Should We Support SAML?]] — enterprise customer request, unresolved
#+end_example

** 2.3 Session Workflow

The recommended post-session workflow:

1. Write the recap while it is fresh
2. Log which clues actually reached the players
3. Update NPC status frontmatter (alive/dead/missing, attitude changes)
4. Let the "next time" block become the prep list for the next session
5. Before the next session, glance at a "DM Screen" MOC that aggregates key info

Session notes gain their value through links: every NPC, location, and
unresolved hook mentioned in the recap gets a [[wikilink]], creating a web of
references that grows richer over time.

** 2.4 Linking Patterns for Non-Tree Knowledge

TTRPG knowledge is inherently a graph, not a tree. The patterns that work:

- *Bidirectional links via backlinks panel*: When NPC "Aldric" links to
  location "Thornwall", the Thornwall page's backlinks panel automatically shows
  Aldric without any manual update.

- *Metadata-based relationships*: Frontmatter fields (=faction=, =location=,
  =leader=) create queryable relationships that Dataview can traverse.

- *Embedded queries on entity pages*: Every location page embeds a Dataview
  query showing "all NPCs whose =location= field matches this page." Every
  faction page shows all members. This creates dynamic, always-current
  relationship views.

- *MOCs as narrative entry points*: A "Campaign Arc: The Dragon War" MOC links
  to all sessions, NPCs, locations, and factions relevant to that arc,
  providing narrative-level navigation.

** 2.5 Pain Points

- *Orphan notes*: Notes with no links in or out accumulate silently. Graph View
  shows them as isolated dots at the periphery. The only defense is discipline:
  every new note must link to at least one existing note.

- *Naming convention drift*: Without strict conventions, the same NPC might be
  referenced as "Aldric", "Aldric Stormborn", "Captain Aldric" --- creating
  multiple unlinked references. Aliases in frontmatter help but require manual
  maintenance.

- *Stale metadata*: Frontmatter fields (status, location, faction) go stale if
  not updated after sessions. No built-in mechanism flags stale data.

- *Link rot*: Renaming a note breaks all wikilinks to it unless you use
  Obsidian's "update links on rename" feature (which only works within the app).
  External references and copy-pasted text with [[brackets]] are not updated.

- *Scale issues with Dataview*: Very large vaults (5000+ notes) can experience
  slow Dataview rendering. Complex DataviewJS queries can freeze the UI.

- *Graph View is mostly decorative*: It looks beautiful but provides limited
  practical utility. You cannot edit notes, create connections, filter by
  metadata, or reorganize spatially. Most experienced users rely on search and
  backlinks instead.

* 3. Obsidian Dataview Query Patterns

** 3.1 Query Language Overview

Dataview has four query types:

- =TABLE= :: Tabular output with columns from metadata fields
- =LIST= :: Simple list of matching notes
- =TASK= :: Extracts checkbox items across notes
- =CALENDAR= :: Calendar visualization of date-based notes

Query structure:

#+begin_example
<QueryType> [fields]
FROM <source>           # folder, tag, or link-based filter
WHERE <condition>       # filter by metadata
SORT <field> [ASC|DESC] # ordering
GROUP BY <field>        # grouping
FLATTEN <field>         # split multi-value fields into rows
LIMIT <number>          # cap results
#+end_example

** 3.2 Practical Query Examples

*** All NPCs in a location (embedded on location page)

#+begin_example
```dataview
TABLE race, class, faction, status
FROM "Characters/NPCs"
WHERE contains(location, this.file.name)
SORT status, file.name ASC
```
#+end_example

*** All faction members

#+begin_example
```dataview
TABLE race, class, location, attitude
FROM "Characters/NPCs"
WHERE contains(faction, this.file.name)
SORT file.name ASC
```
#+end_example

*** Unresolved plot hooks across sessions

#+begin_example
```dataview
LIST
FROM "Campaigns/Dragon-War/Sessions"
WHERE status = "complete"
FLATTEN file.lists AS item
WHERE contains(item.text, "#unresolved")
#+end_example

*** All notes tagged "needs-review"

#+begin_example
```dataview
TABLE file.mtime AS "Last Modified", type
FROM ""
WHERE contains(file.tags, "#needs-review")
SORT file.mtime ASC
```
#+end_example

*** Project status dashboard

#+begin_example
```dataview
TABLE status, due-date, assignee
FROM "Projects"
WHERE status != "done"
SORT due-date ASC
```
#+end_example

*** Notes modified in last 7 days

#+begin_example
```dataview
TABLE file.mtime AS "Modified", file.tags AS "Tags"
FROM ""
WHERE file.mtime >= date(today) - dur(7 days)
SORT file.mtime DESC
```
#+end_example

*** Task rollup grouped by project

#+begin_example
```dataview
TASK
FROM "Projects"
WHERE !completed
GROUP BY file.link
SORT file.name ASC
```
#+end_example

*** NPCs encountered in a specific session (from session page)

#+begin_example
```dataview
TABLE race, faction, attitude
FROM "Characters/NPCs"
WHERE contains(this.npcs-encountered, file.name)
```
#+end_example

** 3.3 Frontmatter vs. Inline Fields

| Aspect              | YAML Frontmatter            | Inline Fields (key:: value)  |
|---------------------+-----------------------------+------------------------------|
| Placement           | Top of file, inside =---=   | Anywhere in document body    |
| Scope               | Whole document              | Specific line/list item      |
| Syntax              | =key: value= (single colon)| =Key:: Value= (double colon) |
| Bracket variant     | N/A                         | =[key:: value]= for inline   |
| Obsidian Properties | Yes (native support)        | No (Dataview-only)           |
| Best for            | Document-level metadata     | Per-item metadata, tasks     |

Best practice: use YAML frontmatter for entity-level metadata (type, status,
location, faction) and inline fields only for per-item annotations within lists
or tables.

** 3.4 FLATTEN and GROUP BY

FLATTEN splits multi-value fields into separate rows --- the inverse of GROUP BY.

#+begin_example
# If an NPC has faction: [Thieves Guild, City Watch]
# FLATTEN creates two rows, one per faction:

```dataview
TABLE file.name AS "NPC", faction
FROM "Characters/NPCs"
FLATTEN faction
GROUP BY faction
```
#+end_example

Order matters: a FLATTENed field is only available after the FLATTEN command.
If you GROUP BY first, then FLATTEN, you get unexpected results.

* 4. Obsidian AI Integration

** 4.1 Plugin Landscape (2025--2026)

Three dominant approaches:

| Approach           | Tool                    | Strength                        |
|--------------------+-------------------------+---------------------------------|
| Semantic discovery | Smart Connections       | Background semantic linking     |
| Chat with vault    | Obsidian Copilot        | Conversational Q&A over notes   |
| Agent integration  | Claude Code + MCP       | Full read/write vault access    |

*** Smart Connections

- Creates AI embeddings of all notes for semantic similarity search
- Runs locally (no cloud required) with a built-in embedding model
- Surfaces "related notes" panel as you write --- finds semantic neighbors
  even without explicit links
- Best for passive discovery: "here are notes related to what you're writing"
- Limitation: read-only, cannot modify notes

*** Obsidian Copilot

- ChatGPT-style conversational interface within Obsidian
- Can query across entire vault contents
- Supports multiple LLM providers (OpenAI, Anthropic, Ollama for local)
- Best for active Q&A: "summarize all sessions mentioning the Dragon Cult"
- Can generate and edit note content

*** Claude Code + MCP (Model Context Protocol)

The most powerful integration as of 2026:

- MCP server runs inside the vault, exposing notes to AI assistants
- Claude Code can list, read, search, and write notes
- Full read/write capability: Claude can create new notes, update frontmatter,
  add links, restructure content
- The vault's =CLAUDE.md= / =AGENTS.md= file defines conventions and workflows
- Multiple MCP server options:
  - =obsidian-claude-code-mcp= plugin: WebSocket on port 22360
  - Local REST API + MCP plugin: HTTP access
  - =mcp-obsidian= (Python server) or =obsidian-mcp-server= (Node)

** 4.2 AI-Ready Vault Architecture

The "LLM Wiki" pattern (popularized by Andrej Karpathy):

#+begin_example
vault/
  raw/              # Human drops material here (immutable)
  raw/processed/    # After AI ingestion, originals move here
  wiki/
    sources/        # AI-processed summaries of raw material
    entities/       # Named entities (tools, people, concepts)
    concepts/       # Abstract ideas and patterns
    index/          # Auto-maintained MOCs
    log/            # Chronological processing log
  CLAUDE.md         # Agent operating instructions:
                    #   - vault structure conventions
                    #   - naming rules
                    #   - how to ingest new sources
                    #   - how to update the index
                    #   - health check workflows
#+end_example

The CLAUDE.md file is critical: it tells the AI agent how the wiki is
structured, what conventions to follow, and what workflows to execute. Without
it, the agent has no way to maintain consistency.

** 4.3 Patterns for Hybrid Human+AI Authoring

Observed patterns:

1. *Human captures, AI promotes*: Human drops rough notes into =raw/=. AI
   reads them, creates structured wiki pages, updates the index, and moves
   originals to =processed/=.

2. *Human writes, AI links*: Human creates content normally. Smart Connections
   surfaces related notes. Human decides which connections to formalize.

3. *Human queries, AI synthesizes*: Human asks a question. Copilot searches
   the vault, reads relevant notes, and produces a synthesized answer with
   source links.

4. *AI health checks*: Periodic vault maintenance --- finding orphan notes,
   stale metadata, missing links, inconsistent naming.

** 5.2 What Denote Already Does Well

*** Naming Convention as Metadata

Denote's filename scheme =YYYYMMDDTHHMMSS--title__keywords.org= encodes the
same information as Obsidian's YAML frontmatter + tags, but at the filesystem
level. This is a significant advantage for external tools: any script (AWK,
grep, find) can filter notes without parsing file contents.

Obsidian equivalent requires opening each file and parsing YAML. Denote's
approach is more unix-friendly and more amenable to CLI/AI tooling.

*** Org-mode Front Matter as Structured Metadata

Org-mode's =#+key: value= syntax is a direct equivalent to YAML frontmatter:

#+begin_example
#+title: Aldric Stormborn
#+date: [2026-07-14]
#+filetags: :npc:faction-thieves-guild:city-thornwall:alive:
#+identifier: 20260714T153022
#+type: npc
#+race: human
#+class: rogue
#+faction: Thieves Guild
#+location: Thornwall
#+status: alive
#+attitude: friendly
#+end_example

This is queryable by denote-query via AWK, and by org-mode's built-in search.
It is also trivially parseable by AI agents reading files directly.

*** Org-agenda for Task Management

Obsidian needs the Tasks plugin + Dataview to approximate what org-agenda does
natively. Org-mode's task management (TODO states, scheduling, deadlines,
clocking, custom agenda views) is strictly superior to Obsidian's approach.

*** Org-capture for Fast Capture

Obsidian needs QuickAdd to match org-capture's speed. Org-capture templates
with keybindings are faster and more customizable than QuickAdd macros.

*** Silos as Vault Boundaries

Denote's silo concept (separate directories with =.dir-locals.el=) maps
directly to Obsidian's multi-vault approach, with the same trade-off: notes in
separate silos cannot link to each other.

** 5.3 What denote-query Needs to Match Dataview

*** Already Feasible (AWK-based)

These Dataview patterns can be implemented with denote-query's AWK approach:

1. *Search by field value*: Find all files where =#+type: npc= and
   =#+location: Thornwall=. This is straightforward AWK pattern matching on
   org front matter lines.

2. *List with field extraction*: List all NPCs showing name, race, faction.
   AWK reads front matter fields, outputs as table rows.

3. *Backlinks*: Find all files that contain a link to a given denote ID.
   Already implemented in denote itself; denote-query can wrap this.

4. *Tag-based filtering*: Find all files with =:needs-review:= in filetags.
   Trivial with AWK on the =#+filetags:= line, or even with filename-based
   grep on =__needs-review=.

5. *Sort by date*: Denote's timestamp-first filename means =ls= already sorts
   chronologically. AWK can sort by any front matter field.

6. *Recently modified*: =find= with =-mtime= or =stat= on modification time.

*** Requires Extension

These patterns need new denote-query subcommands or post-processing:

1. *TABLE output*: Formatted table output with configurable columns extracted
   from front matter fields. AWK can produce this but needs a defined output
   format (org table syntax would be natural).

2. *WHERE with expressions*: Filtering by field comparisons (=status != done=,
   =level > 5=). AWK can do this but the query syntax needs design.

3. *GROUP BY*: Aggregating results by a field value (all NPCs grouped by
   faction). AWK can accumulate into arrays and output grouped results.

4. *FLATTEN*: Splitting multi-value fields. If =#+faction: Thieves Guild,
   City Watch=, produce two result rows. AWK string splitting handles this.

5. *Cross-reference queries*: "All NPCs whose location matches THIS note's
   title." Requires the query to read the current file's metadata and use it
   as a filter parameter. This is the =this.file.name= equivalent.

6. *Embedded dynamic queries*: Dataview queries live inside the note and render
   dynamically. In org-mode, the closest equivalent is =#+begin_src= blocks
   with =:results output= that can be re-evaluated. This is a significant UX
   difference --- Dataview is always live; org blocks require manual C-c C-c.

*** Probably Not Worth Replicating

1. *Graph View*: Obsidian's own community considers it mostly decorative. A
   DOT graph generator would be a fun experiment but low practical value.

2. *Canvas*: Obsidian's infinite whiteboard has no org-mode equivalent and
   building one would be a massive effort for marginal gain.

3. *Properties panel*: GUI metadata editing. Emacs users edit text directly;
   a properties panel adds no value.

4. *Smart Connections (semantic search)*: Requires embedding infrastructure.
   Better handled by Claude Code reading the vault directly than by
   reimplementing a semantic search engine.

** 5.4 Recommended denote-query Subcommands

Based on the Dataview patterns most commonly used in practice:

*** Priority 1: Core Queries

#+begin_example
# List notes matching field criteria (Dataview TABLE equivalent)
denote-query table --fields "title,race,faction,status" \
                   --where "type=npc" \
                   --where "location=Thornwall" \
                   --sort "status,title" \
                   --format org-table

# Simple list with filtering
denote-query list --where "type=location" \
                  --where "region=Northlands" \
                  --sort "title"

# Backlinks to a specific note
denote-query backlinks 20260714T153022

# Search by tag
denote-query tagged "needs-review"

# Recently modified notes
denote-query recent --days 7
#+end_example

*** Priority 2: Relationship Queries

#+begin_example
# Cross-reference: notes linking TO a given note
denote-query links-to 20260714T153022

# Cross-reference: notes linked FROM a given note
denote-query links-from 20260714T153022

# Orphan detection: notes with no incoming or outgoing links
denote-query orphans

# Notes matching field value of CURRENT file (for embedded use)
denote-query table --fields "title,race,status" \
                   --where "type=npc" \
                   --where "location=$(denote-query field title $CURRENT_FILE)" \
                   --format org-table
#+end_example

*** Priority 3: Aggregation

#+begin_example
# Group by field value
denote-query group-by faction --where "type=npc" --format org-table

# Count by field value
denote-query count-by status --where "type=npc"

# Flatten multi-value field
denote-query table --fields "title,faction" \
                   --where "type=npc" \
                   --flatten faction \
                   --format org-table
#+end_example

  lore/                             # Silo: worldbuilding lore
    20260714T170000--the-sundering__history_cosmology.org
    20260714T170100--arcane-magic-system__magic_rules.org
  gm-tools/                         # Reference material
    20260714T180000--random-npc-generator__tool_table.org
#+end_example

Key differences from the Obsidian approach:

- Entity /type/ goes into both the subdirectory (for browsing) and the keywords
  (for querying): =__npc= in the filename makes AWK filtering trivial.
- /Relationships/ go into org front matter fields (=#+faction:=, =#+location:=)
  rather than the filename, since filenames can't hold structured metadata.
- /Status/ fields (alive/dead, draft/complete) go into front matter for
  queryability, but key statuses can also be keywords for quick filesystem
  filtering.

** 5.8 Summary: What to Build, What to Skip

*** Build (High Value, Feasible)

1. =denote-query table= :: AWK-based field extraction + org-table output.
   This is the single highest-value feature. It covers 60%+ of Dataview usage.

2. =denote-query list= :: Filtered note lists. Simpler version of table.

3. =denote-query backlinks= / =links-to= :: Find notes referencing a given ID.

4. =denote-query orphans= :: Find unlinked notes. Trivial with link analysis.

5. =denote-query recent= :: Recently modified notes. Uses filesystem metadata.

6. =denote-query count-by= :: Aggregate counts by field value. Quick vault
   health metrics.

7. Shell-block integration pattern :: Document the pattern of embedding
   =denote-query= calls in =#+begin_src shell= blocks for semi-dynamic
   queries (re-evaluate with C-c C-c).

*** Consider (Medium Value)

8. =denote-query group-by= :: Grouped output. Useful for dashboards.

9. =denote-query flatten= :: Multi-value field splitting. Needed for
   many-to-many relationships (NPC in multiple factions).

10. =denote-query graph= :: DOT output for Graphviz rendering. Fun but
    niche utility.

11. =denote-query unlinked-mentions= :: Find notes whose title appears in
    other notes' body text without a formal link.

*** Skip (Low Value or Wrong Tool)

12. Live/reactive queries (Dataview's auto-refresh). Org-mode's
    evaluate-on-demand model is different but adequate.

13. Canvas equivalent. Wrong layer --- use a separate tool if needed.

14. Semantic search. Let Claude Code handle this by reading the vault.

15. GUI metadata editor. Emacs users don't need or want this.

* 6. Key Takeaways

** For Project Knowledge Bases

1. The =raw/ -> wiki/= pipeline (immutable sources, living synthesis) is a
   powerful pattern that translates directly to Denote with two silos.

2. MOCs emerge naturally from note accumulation --- don't create them
   prematurely. In Denote, structure notes serve the same purpose.

3. An =AGENTS.md= or equivalent file defining vault conventions is essential
   for AI integration, regardless of whether you use Obsidian or Emacs.

** For TTRPG / Worldbuilding

4. Entity templates with consistent frontmatter fields are the foundation.
   The specific fields (type, faction, location, status) are universal across
   all TTRPG vaults.

5. Embedded queries on entity pages ("show all NPCs in this location") are
   the killer feature that makes a vault feel like a living wiki rather than a
   pile of files. This is the highest-priority denote-query capability.

6. Session notes are the /input/ to the system; entity pages are the /state/.
   The workflow is: write session recap, update entity metadata, let queries
   surface the current world state.

** For AI Integration

7. The MCP approach (Claude Code reading/writing vault files) works identically
   with org files on the filesystem. No Obsidian-specific infrastructure needed.

8. The most valuable AI operations are: ingest raw material into structured
   notes, find orphan/stale notes, answer questions by searching the vault.

9. Denote's filename convention is /more/ AI-friendly than Obsidian's approach
   because metadata is visible at the filesystem level without opening files.
