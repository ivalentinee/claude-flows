* Constraint Analysis: Extending Denote for General Project Knowledge DB

** Analyst: Constraint Analyst
** Date: 2026-07-14

** Summary

This analysis identifies hard constraints, soft constraints,
anti-constraints, and key trade-offs for extending the denote system
from a design artifact manager to a general-purpose project knowledge
DB serving three goals: code-undiscoverable facts, genuine knowledge
graphs, and Claude context optimization.

** A. Filesystem Constraints

*** Hard Constraints

1. *Denote is purely file-based.* All queries run against the
   filesystem via grep/AWK. There is no database, no index file that
   survives across sessions. Every query re-scans. This is a feature
   (always fresh) but sets a performance ceiling.

2. *AWK front matter scanner assumes homogeneity.* The current
   =denote-query= AWK core (lines 100-133 of the script) scans from
   line 1 until the first =*= heading, extracting exactly 5 fields:
   title, filetags, identifier, signature, deferred. This is hardcoded
   for the design artifact schema. Knowledge notes with different front
   matter (e.g., =#+type: god=, =#+domain: religion=, =#+related:=)
   would require AWK modifications or a second scanner.

3. *Cross-links use =[[file:]]= with relative paths.* Org-mode file
   links are path-based. If knowledge and designs live in different
   directories, links become =[[file:../designs/foo.org]]= or
   =[[file:../knowledge/bar.org]]=. These work but are fragile under
   renames and harder to grep (the path prefix varies).

*** Soft Constraints

1. *Grep-based querying scales well for the projected range.* The
   denote-flow-linking research measured <20ms for all queries at 200
   files. Zettelkasten practitioners report usable grep performance up
   to ~2000-5000 notes. A TTRPG setting with 500 notes is well within
   this range. At 5000+ notes, AWK scanning starts to feel sluggish
   (100-200ms) but remains functional.

2. *Heterogeneous note types are handleable but require schema
   extension.* The current type vocabulary (research, design,
   sub-feature, review, supporting) would need expansion (e.g., lore,
   character, location, rule, fact). The open filetag system already
   supports this -- adding =:lore:= or =:character:= requires zero
   code changes. But the section extraction subcommands (goals,
   constraints, deferred-items) are design-specific and would not apply
   to knowledge notes.

*** Key Finding

The AWK scanner is extensible but not polymorphic. It extracts the
same 5 fields from every file. Knowledge notes that need additional
structured fields (e.g., =#+related:=, =#+category:=) would either:
(a) pack everything into filetags (ugly but works with current
tooling), or (b) require new front matter fields and AWK extraction
logic. Option (b) is cleaner but means the scanner must handle both
schemas.

** B. Claude Code Tool Constraints

*** Hard Constraints

1. *Claude has exactly 4 relevant tools: Glob, Grep, Read, Bash.*
   The =denote-query= script is called via Bash. This is the only
   programmatic query interface. There is no SQLite, no embeddings,
   no vector search.

2. *Context window is 1M tokens.* This is generous but not infinite.
   The token analysis from the denote research shows:
   - 500 notes, front matter only: ~3,900 tokens (trivial)
   - 500 notes, all content: ~50K-100K tokens (manageable)
   - 500 notes, full documents: ~2.4M tokens (exceeds window)

   For a TTRPG setting with 500 notes averaging 100-200 tokens each
   (atomic lore facts), reading ALL content is ~50-100K tokens. This
   is well within the 1M budget. The two-stage pattern (metadata
   filter then content read) remains effective but is less critical
   for small notes than for large design documents.

3. *Tool calls have overhead.* Each Bash/Read call costs ~50 tokens
   in protocol overhead. The denote research found that batch
   extraction via =denote-query= eliminates per-file Read calls
   (one Bash call replaces 10-200 Read calls). This advantage is
   equally relevant for knowledge notes.

*** Soft Constraints

1. *The two-stage pattern scales well for 500 small notes.* Reading
   all front matter for 500 notes is ~5K tokens. If filtering narrows
   to 20-50 relevant notes, reading their content adds ~2K-10K tokens.
   Total: ~7K-15K tokens per query. This is cheap relative to the 1M
   budget.

2. *Full-corpus reads are feasible for small-note knowledge bases.*
   Unlike design documents (3K-50K tokens each), knowledge notes are
   expected to be small (atomic facts: 50-200 tokens; lore entries:
   200-1000 tokens). Reading all 500 notes' content (~50-100K tokens)
   is feasible for compilation tasks ("generate all gods and
   religions").

*** Key Finding

The bottleneck shifts for knowledge notes. For design artifacts, the
bottleneck is content size (large documents). For knowledge notes, the
bottleneck is note count (many small files). The two-stage pattern is
still valuable, but the "compile all tagged X" operation (reading 50-200
small notes at once) is practical in ways that "read all design docs"
never would be.

** C. Directory Structure Constraints

*** Hard Constraints

1. *=denote-query= defaults to =--dir designs/=.* The script accepts
   =--dir= to override this. Cross-directory queries require either:
   (a) calling the script twice with different =--dir= values, or
   (b) passing a merged file list via =--files=. Neither is
   particularly elegant.

2. *=[[file:]]= links are path-relative.* A link from
   =designs/foo.org= to =knowledge/bar.org= must use
   =[[file:../knowledge/bar.org]]=. A link from =knowledge/bar.org=
   to =designs/foo.org= must use =[[file:../designs/foo.org]]=. The
   backlinks subcommand (grep for filename) works across directories
   only if the grep path includes both directories.

*** Trade-Off Analysis: Directory Structure

**** Option 1: Single directory (knowledge + designs mixed)

Pros:
- All queries work with default =--dir designs/=
- =[[file:]]= links are simple (same directory)
- Backlinks grep is trivial (one directory)
- No cross-directory linking complexity

Cons:
- =ls= output is cluttered (design artifacts mixed with lore notes)
- No scope separation (convergence gate scans knowledge notes too)
- Tag-based filtering must compensate for the lack of directory-based
  scoping
- Semantically different concerns share a namespace

Verdict: Workable for small corpora. Breaks down at 100+ knowledge
notes mixed with 50+ design artifacts. The convergence gate would
scan ALL notes, including irrelevant knowledge notes, adding noise.

**** Option 2: Separate directories (designs/ and knowledge/)

Pros:
- Clean separation of concerns
- =ls= output is scoped and clean
- Convergence gate scans only designs/ (default behavior unchanged)
- Knowledge queries scope to knowledge/ via =--dir knowledge/=

Cons:
- Cross-directory =[[file:]]= links require relative paths (=../=)
- Backlinks need multi-directory grep
- =denote-query= must be called separately per directory, or given
  a =--dir= that covers both
- Two mental models for "where does this note live?"

Verdict: Best separation of concerns. The cross-linking cost is real
but manageable -- org-mode handles relative paths fine.

**** Option 3: Sibling directories under a common parent

Structure: =project/designs/= and =project/knowledge/=, with
=denote-query --dir project/= scanning both.

Pros:
- Single =--dir= covers both (recursive scan)
- Separation via subdirectories, unified via parent
- Cross-links use relative paths within the same parent

Cons:
- Requires restructuring: current =designs/= would become
  =project/designs/= or =--dir .= must encompass the working
  directory
- Convergence gate now scans both directories (knowledge notes
  may show as false positives)
- =denote-query= subcommands designed for design artifacts
  (goals, constraints) would fail on knowledge notes (no such
  headings)

Verdict: Theoretically clean but practically disruptive. The current
system assumes =designs/= at the top level. Moving it into a parent
directory breaks existing paths, flow references, and the default
=--dir=.

**** Recommendation (preliminary)

Option 2 (separate directories) is the strongest choice. The cross-
linking cost is bounded and well-understood. The =--dir= flag already
exists. The key requirement is a way to query across both directories
when needed (e.g., =denote-query --dir . --exclude designs/= or a
=--dirs= flag accepting multiple directories).

** D. Hybrid Maintenance Constraints

*** Hard Constraints

1. *No file locking mechanism.* Org files are plain text. If both
   human and Claude edit the same file, the last writer wins. There
   is no merge mechanism, no conflict detection, no version control
   within the denote system itself.

2. *Claude's memory system is auto-managed.* The memory files in
   =~/.claude/projects/*/memory/= are written by Claude Code's
   built-in memory system. They have a specific format (YAML front
   matter + markdown body). The user does not typically edit these
   directly, though they can. Claude does not typically read these
   on demand -- they are loaded at session start.

*** Soft Constraints

1. *Authorship tracking is desirable but not enforced.* A filetag
   like =:human-authored:= or =:claude-authored:= could distinguish
   origin, but mixed-edit notes (human creates, Claude refines) don't
   fit a binary model. A =#+author:= front matter field is more
   flexible but adds schema complexity.

2. *Conflict avoidance is more practical than conflict resolution.*
   If knowledge notes are small and atomic (Zettelkasten principle),
   editing the same note simultaneously is unlikely. The bigger risk
   is Claude updating a note that the human has locally modified
   outside the session. Git tracking of knowledge files would provide
   a safety net (diff before overwrite).

*** Key Finding

The hybrid maintenance question is less about technical conflicts and
more about ownership semantics. Three ownership models:

| Model             | Human writes         | Claude writes        | Both edit |
|-------------------+----------------------+----------------------+-----------|
| Human-primary     | Lore, world-building | Never (read-only)    | No        |
| Claude-primary    | Never                | Discovered facts     | No        |
| Shared            | Initial drafts       | Refinements, links   | Yes       |

For code-undiscoverable facts (Goal 1), Claude-primary makes sense:
Claude discovers a fact and persists it. For TTRPG lore (Goal 2),
human-primary with Claude as reader/compiler makes sense. The system
should support all three models without mandating one.

** E. Output Generation Constraints

*** Hard Constraints

1. *=denote-query= has no "compile" subcommand.* The existing
   subcommands filter and extract, but do not compose. A "compile all
   notes tagged =:god:=" operation would need to:
   (a) Filter by tag (=denote-query tag god --format paths=)
   (b) Read all matching files' content
   (c) Assemble into a coherent document with ordering and narrative

   Step (c) is a Claude reasoning task, not a script task. The script
   can provide (a) and (b); Claude provides (c).

2. *No ordering mechanism in denote metadata.* The =#+identifier:=
   field provides chronological order (creation time). But TTRPG
   content needs semantic ordering (gods grouped by pantheon, sorted
   by importance). This requires either:
   (a) A =#+order:= or =#+weight:= front matter field
   (b) Hierarchical tags (=:pantheon-celestial:god:=)
   (c) A "table of contents" note that defines the order
   (d) Claude infers order from content (most flexible, least
       reproducible)

*** Soft Constraints

1. *The existing =denote-query goals --filter TAG= pattern is close.*
   It extracts specific sections from files filtered by tag. A
   "compile" operation is conceptually similar: extract ALL content
   (not just Goal) from files filtered by tag, then assemble. The
   missing piece is the assembly/weaving step.

2. *Compilation templates could be knowledge notes themselves.* A note
   titled "Religion Compendium Template" with tags =:template:religion:=
   could define the structure of the compiled output (section order,
   narrative framing). Claude reads the template, then fills it by
   querying tagged knowledge notes. This is a meta-note pattern
   (Zettelkasten "structure notes").

*** Key Finding

Output generation is fundamentally a two-step process: (1) retrieval
(=denote-query= handles this) and (2) synthesis/weaving (Claude handles
this). The denote system does not need a "compile" subcommand because
Claude IS the compiler. What it needs is good retrieval primitives
(filter by tag, read all content, return in a useful format). The
current tooling is ~80% there. The gap is:

- A subcommand that returns full note content (not just sections) for
  a set of files: =denote-query content --filter TAG= (returns all
  content between the first =*= heading and EOF, or between the
  front matter and EOF)
- Ordering support (=#+order:= field or tag-based sorting)

** F. Boundary with Claude Code Memory System

*** Current Memory System Analysis

The Claude Code memory system (=~/.claude/projects/*/memory/=)
currently contains 9 files for the =-app= project:

| File                              | Content type                     |
|-----------------------------------+----------------------------------|
| MEMORY.md                         | Index (links to other files)     |
| feedback_code_principles.md       | Elixir/Phoenix coding idioms     |
| feedback_flow_guide.md            | Which flow to use                |
| feedback_full_flow.md             | Full flow preference             |
| feedback_design_process.md        | Design flow preference           |
| feedback_implementation_process.md| Impl flow preference             |
| feedback_research_flow.md         | Research flow preference         |
| feedback_testing_approach.md      | E2E test preference              |
| feedback_no_user_review.md        | Review discipline rules          |
| project_scaling_bugs.md           | Active bug IDs and conventions   |

Pattern: memory files are either /behavioral directives/ (how Claude
should behave) or /project state/ (what is currently in progress).
They are auto-loaded at session start and guide Claude's behavior
without explicit retrieval.

*** Hard Constraints

1. *Memory is auto-loaded; knowledge requires explicit retrieval.*
   Memory files are injected into every conversation. Knowledge notes
   would be retrieved on demand via =denote-query=. This is a
   fundamental architectural difference: memory is "always in context"
   while knowledge is "queryable on demand."

2. *Memory has a YAML front matter format; knowledge uses Org front
   matter.* The two systems use incompatible metadata schemas. Memory
   files have =name=, =description=, =type= in YAML. Knowledge notes
   have =#+title:=, =#+filetags:=, =#+identifier:= in Org. They
   cannot be queried with the same tooling without adaptation.

3. *Memory is project-scoped; knowledge may be cross-project.* Memory
   lives at =~/.claude/projects/<project>/memory/=. Knowledge could
   be project-specific (code facts about Idunn) or project-independent
   (TTRPG worldbuilding). The denote system's =--dir= flag supports
   pointing to different knowledge bases, but the memory system is
   inherently tied to a project.

*** Boundary Definition

| Characteristic          | Memory                    | Knowledge DB              |
|-------------------------+---------------------------+---------------------------|
| Loaded when             | Auto, every session       | On demand, via query      |
| Written by              | Claude (auto-managed)     | Human + Claude (hybrid)   |
| Format                  | YAML + Markdown           | Org front matter + body   |
| Scope                   | Per-project               | Per-project or standalone |
| Content type            | Behavioral directives     | Facts, lore, references   |
| Size per entry          | 5-20 lines                | Varies (50-5000+ tokens)  |
| Query mechanism         | Auto-load (no query)      | =denote-query= script     |
| Persistence across runs | Yes (file-based)          | Yes (file-based)          |

*** Where Code-Undiscoverable Facts Should Live

This is the crux of the boundary question. Consider these examples:

| Fact                                         | Memory? | Knowledge? |
|----------------------------------------------+---------+------------|
| "Elixir fields use snake_case with source:"  | Yes     | No         |
| "Port comm was replaced by Unix sockets"     | No      | Yes        |
| "Use E2E tests, not unit tests"              | Yes     | No         |
| "The compiler pipeline is: Parse -> Resolve  |         |            |
|  -> Validate -> Expand -> Bind -> Generate"  | No      | Yes        |
| "Bug 15864 has 5 sub-bugs for scaling"       | Yes     | No         |
| "RabbitMQ retry logic uses exponential       |         |            |
|  backoff with max 30s delay"                 | No      | Yes        |

The distinction: *behavioral directives* ("do X, not Y") belong in
memory. *Factual knowledge* ("the system works like X") belongs in the
knowledge DB. Memory shapes Claude's behavior; knowledge informs
Claude's reasoning.

*** Risk: Two Competing Persistence Systems

Real risk. Mitigations:

1. *Clear boundary rule:* If it starts with "always/never/prefer" or
   describes Claude's behavior, it is memory. If it describes how the
   system works or contains domain knowledge, it is knowledge.

2. *No overlap in tooling:* Memory uses YAML + Markdown, loaded
   automatically. Knowledge uses Org + denote-query, loaded on demand.
   Different formats make accidental mixing unlikely.

3. *Migration path for existing memory:* =project_scaling_bugs.md=
   arguably contains factual knowledge (bug IDs), not behavioral
   directives. It could migrate to the knowledge DB. But it is also
   ephemeral project state -- it will be irrelevant once the bugs are
   fixed. Short-lived project state probably stays in memory; enduring
   knowledge goes in the knowledge DB.

*** Key Trade-offs

**** T1: Schema uniformity vs. expressiveness

Uniform schema (all notes use the same 5 front matter fields):
- Pro: One scanner, one query interface, one mental model
- Con: Filetags become overloaded; no room for domain-specific metadata
  (=#+pantheon:=, =#+related-gods:=)

Extended schema (knowledge notes add domain-specific fields):
- Pro: Rich metadata for domain queries ("all gods in the Celestial
  pantheon")
- Con: AWK scanner must handle variable schemas; query subcommands
  diverge

Recommendation: Start uniform. Use filetags for domain categorization.
Add domain-specific fields only when filetag-based queries prove
insufficient. The open tag system already supports =:god:celestial:=
without schema changes.

**** T2: Single directory vs. separate directories

Already analyzed in Section C. Recommendation: separate directories
with a mechanism for cross-directory queries (=--dir= or =--dirs=).
The convergence gate should NOT scan knowledge notes by default.

**** T3: Memory vs. knowledge DB for code-undiscoverable facts

Behavioral directives in memory; factual knowledge in knowledge DB.
But edge cases exist (bug IDs are facts that shape behavior). Accept
some overlap at the boundary rather than over-engineering the
distinction.

**** T4: Status lifecycle for knowledge notes

Design artifacts have a clear lifecycle (active -> designed ->
implemented). Knowledge notes may not. A TTRPG god note is not
"implemented" -- it is "draft" or "canonical" or "retconned." The
status vocabulary needs either: (a) a separate set for knowledge
notes, or (b) knowledge notes opt out of status tracking entirely
and use only filetags for categorization.

Recommendation: Knowledge notes opt out of status suffixes in
filenames. They use filetags for categorization (=:god:celestial:=)
and may optionally have a =:draft:= or =:canonical:= status, but
this is domain-specific and not enforced by the system.

**** T5: Compilation ordering

No current mechanism for semantic ordering. Options:
(a) =#+order:= field (explicit, verbose for 500 notes)
(b) Structure notes (a "table of contents" note that references others
    in order -- Zettelkasten pattern)
(c) Claude infers order from content at compilation time

Recommendation: Structure notes (option b). They are knowledge notes
themselves, tagged with =:structure:=, and define the compilation
order by listing =[[file:]]= references. This reuses existing linking
conventions and is human-editable. Claude reads the structure note to
determine what to compile and in what order.

* External Survey: How Others Solve Similar Problems

** Surveyor: External Surveyor
** Date: 2026-07-14

** Summary

Conducted external research across five topic areas to understand how
others solve the problem of file-based project knowledge management,
knowledge graphs, and AI context optimization. Fetched and analyzed
15+ external sources including Karpathy's LLM Wiki gist, Zettelkasten
methodology documentation, Vannevar Bush's Memex concept, worldbuilding
tools (LegendKeeper), digital garden theory (Maggie Appleton), AI
coding tools (GitHub Copilot, Cursor, Aider), AI memory systems (Mem0,
GraphRAG, Kotaemon), and knowledge management approaches (denote,
org-roam, Obsidian, Gwern.net, TIL pattern, nb).

** Key Findings

*** Finding 1: Karpathy's LLM Wiki is the closest external model

Karpathy's gist describes a three-layer architecture (raw sources /
LLM-maintained wiki / schema) with three operations (ingest / query /
lint). His key insight: "The tedious part of maintaining a knowledge
base is not the reading or the thinking --- it's the bookkeeping."
This directly validates the approach of having Claude maintain
knowledge notes while humans curate.

Production finding: schema quality determines system quality. Drift
(stale cross-references) is the primary failure mode, addressed by
regular lint operations.

*** Finding 2: All successful knowledge systems converge on atomic notes

Zettelkasten, TIL repositories (~1820 notes), digital gardens, Karpathy's
wiki, and worldbuilding tools all use single-topic notes as the
fundamental unit. Structure/hub notes provide navigation. Tags provide
cross-cutting categorization. This validates the denote approach.

*** Finding 3: Explicit links carry meaning that search cannot replicate

The zettelkasten.de site explicitly states: "full-text search on its
own provides not enough material." Links encode semantic relationships
(this-depends-on, this-contradicts, this-extends) that grep cannot
discover. Worldbuilding tools go further with typed relationships.

*** Finding 4: Staleness is the universal failure mode

Every knowledge system surveyed identifies stale, unmaintained notes as
the primary failure mode. Karpathy's lint operation, digital garden
epistemic status markers, and Mem0's temporal reasoning all address
this. No current denote-style tool has built-in staleness detection.

*** Finding 5: Compiled views are needed for AI context optimization

Anthropic's prompt caching requires a minimum of 4096 tokens per cached
block (for Opus). Individual atomic notes will be too small to cache.
Compiled views that bundle related notes into context-optimized
documents are necessary. No existing note-taking tool provides this.

*** Finding 6: No existing tool combines file-based notes with AI maintenance

This is a genuine gap. Karpathy describes the concept. Mem0 implements
AI memory but uses a vector database (not files). Obsidian has plugins
but no AI maintenance. The proposed system would occupy a unique
position: file-based, git-tracked, AI-maintained knowledge notes.

*** Finding 7: Worldbuilding tools demonstrate the value of typed relationships

LegendKeeper's auto-linking and Obsidian's Dataview plugin show that
typed relationships enable queries impossible with flat links:
"all entities in faction X," "all events caused by character Y."
A project KB may need lightweight typed relationships for
dependency chains, convention scoping, and decision tracking.

** Recommendation

Option D (Hybrid Atomic Notes + Compiled Views) synthesizes the strongest
patterns from external research. It combines denote-style atomic files,
Karpathy-inspired AI maintenance with lint operations, lightweight typed
relationships from worldbuilding tools, and compiled views optimized for
prompt caching. This addresses all three stated goals (code-undiscoverable
facts, knowledge graph, AI context optimization) while remaining
file-based, git-tracked, and portable.
