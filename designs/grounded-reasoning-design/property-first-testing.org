#+TITLE: Property-First Test Design
#+SUBTITLE: Enumerating Behavioral Properties Before Writing Test Code
#+DATE: 2026-07-31

* 1. The Concept and Its Names

The practice of explicitly listing which behavioral properties a test
should validate /before/ writing test code does not have a single
canonical name. Instead, it sits at the intersection of several
well-established practices:

** 1.1 Kent Beck's "Test List" (Canon TDD)

The closest direct match is Beck's first step in canonical TDD, which
most practitioners skip. In his "Canon TDD" clarification, Beck defines
a five-step process where Step 1 is: "Write a list of the test scenarios
you want to cover."

Beck explicitly warns that people miss this step: "Folks seem to have
missed this step in the book. 'TDD just launches into coding.' Nope."

The test list is a /behavioral/ planning artifact: enumerate the
scenarios, not the implementation. Beck further warns against mixing
implementation decisions into this phase: "Chill. There will be plenty of
time to decide how the internals will look later."

Source: https://newsletter.kentbeck.com/p/canon-tdd

** 1.2 OASIS Test Assertion Guidelines

The OASIS standard provides the most formal framework. A "test
assertion" is defined as "a testable or measurable expression for
evaluating the adherence of an implementation to a normative statement in
a specification." Each assertion has five components:

1. *Identifier* -- unique reference for traceability
2. *Normative Source* -- the requirement being tested
3. *Target* -- what component is under test
4. *Predicate* -- the logical expression (true/false)
5. *Prescription Level* -- mandatory (MUST), preferred (SHOULD), or
   permitted (MAY)

The derivation methodology: analyze each normative statement, break
compound requirements into discrete assertions, establish prerequisites,
and assign targets. This is property enumeration formalized.

Source: https://docs.oasis-open.org/tag/guidelines/v1.0/testassertionsguidelines.html

** 1.3 Kent Beck's Test Desiderata

A complementary but distinct concept. The Test Desiderata describes
properties of tests /themselves/ (meta-properties), not properties of
the system under test. The twelve desiderata are: isolated, composable,
deterministic, fast, writable, readable, behavioral, structure-insensitive,
automated, specific, predictive, and inspiring.

The key desideratum for property-first design is *behavioral*: "tests
should be sensitive to changes in the behavior of the code under test."
This implies the test author must first identify /which/ behaviors to be
sensitive to.

Source: https://medium.com/@kentbeck_7670/test-desiderata-94150638a4b3

** 1.4 BDD Specification by Example

BDD's Given-When-Then format (Terhorst-North and Matts) is another
expression of property-first thinking. The scenario declares the expected
behavioral outcome /before/ any implementation exists:

- Given (preconditions) -- the state of the world
- When (action) -- the behavior under test
- Then (properties) -- what must be true afterward

The "Then" clause is the property enumeration.

** 1.5 Property-Based Testing Property Selection

Scott Wlaschin's "Choosing Properties for Property-Based Testing"
provides seven categories for discovering testable properties:

1. Different paths, same destination (commutativity)
2. There and back again (inverse operations)
3. Some things never change (invariants)
4. The more things change, the more they stay the same (idempotence)
5. Solve a smaller problem first (structural induction)
6. Hard to prove, easy to verify (verification asymmetry)
7. The test oracle (comparison with alternate implementation)

These categories are a property /discovery/ framework -- answering
"which properties exist?" before "how do I test them?"

Source: https://fsharpforfunandprofit.com/posts/property-based-testing-2/

* 2. Proposed Name: Property-First Test Design

Since no single term captures this practice, we adopt "Property-First
Test Design" to mean: /explicitly enumerate which behavioral properties
a test should validate before writing the test code/.

This is distinct from:
- *Test-first development* (TDD) -- which says write the test before
  the code, but does not emphasize enumerating properties before
  writing the test
- *Property-based testing* (QuickCheck) -- which tests properties with
  random inputs, but the challenge of /choosing/ properties remains
- *Specification-first testing* -- which derives tests from a spec
  that may already exist, rather than constructing the property list
  as a design act

Property-First Test Design adds a step /before/ TDD's red phase:
the property enumeration step.

* 3. The Property Checklist Framework

For an HTTP API endpoint, the property checklist looks like:

** 3.1 Functional Properties

| Property Class          | Example Check                          | Priority |
|-------------------------+----------------------------------------+----------|
| Response status code    | 200 for success, 404 for missing       | P0       |
| Response body structure | Required fields present, correct types | P0       |
| Response body values    | Correct data returned for given input  | P1       |
| Error response format   | Consistent error body structure        | P1       |
| Error codes             | Correct status for each error case     | P1       |
| Input validation        | Rejects malformed input with 400/422   | P1       |
| Edge cases              | Empty collections, boundary values     | P2       |
| Idempotency             | Repeated identical requests, same result| P2      |

** 3.2 Contract Properties

| Property Class          | Example Check                          | Priority |
|-------------------------+----------------------------------------+----------|
| Schema conformance      | Response matches OpenAPI/JSON Schema   | P0       |
| Required headers        | Content-Type, CORS headers present     | P1       |
| Caching headers         | Cache-Control set correctly            | P2       |
| Security headers        | HSTS, X-Frame-Options present          | P2       |

** 3.3 Operational Properties

| Property Class          | Example Check                          | Priority |
|-------------------------+----------------------------------------+----------|
| Response time           | Under latency SLO                      | P2       |
| Timeout behavior        | Graceful handling of slow dependencies | P3       |
| Resource cleanup        | No connection leaks, no temp files     | P3       |

** 3.4 The Enumeration Process

Before writing any test code:

1. List every property class from the checklist above
2. For each, decide: test now, test later, or never test
3. For "test now," write the specific predicate (e.g., "status = 200")
4. For "test later," record as a TODO with a trigger condition
5. For "never test," record the reason (e.g., "framework handles this")

This produces a property manifest -- a document that IS the
specification for what the test suite should cover.

* 4. Gradual Enforcement Pattern

** 4.1 The Concept

No established name exists for the pattern of starting with loose
property checks and progressively tightening them. The closest related
concepts are:

- *Test Maturity Model (TMM)* -- organizational maturity levels for
  testing processes, but these describe process maturity, not assertion
  strictness within individual tests
- *API assertion strictness levels* -- an emerging practice in API
  testing that recognizes a natural progression

** 4.2 Three Levels of Assertion Strictness

From the API testing literature, a natural progression emerges:

*Level 1 -- Smoke (status only):*
Assert the response status code is correct. This catches catastrophic
failures: endpoint not found, server errors, auth failures. A single
assertion. Takes minutes to write.

*Level 2 -- Schema (structure):*
Assert the response body conforms to a JSON Schema or type definition.
Required fields are present, types are correct, no unexpected fields.
This catches structural regressions without asserting specific values.

*Level 3 -- Semantic (values and behavior):*
Assert specific field values, business logic correctness, and
behavioral properties like idempotency. This catches logic bugs.

** 4.3 Progressive Tightening as a Strategy

The gradual enforcement pattern works as follows:

1. *Sprint 1*: Write Level 1 tests for all endpoints. Coverage is
   broad but shallow. Takes hours, not days.
2. *Sprint 2*: Promote critical endpoints to Level 2. Add schema
   validation. Catches structural drift.
3. *Sprint 3*: Promote business-critical paths to Level 3. Add value
   assertions for fields that matter.
4. *Ongoing*: When a bug is found, add the missing property assertion
   at the appropriate level. Each bug makes the suite stricter.

This is not about writing bad tests and improving them later. It is
about acknowledging that comprehensive Level 3 coverage for every
endpoint on day one is unrealistic, and that Level 1 coverage for
everything is better than Level 3 coverage for nothing.

** 4.4 Mutation Testing as Strictness Validator

Mutation testing reveals which level your assertions actually operate
at. A surviving mutant names a code location and a transformation that
no assertion noticed -- that is where the missing property lives.

Code coverage can reach 100% with zero assertions. Mutation score
measures whether assertions would have /noticed/ if the code behaved
differently. It is the empirical measure of assertion strictness.

* 5. Integration with TDD-as-Grounding

** 5.1 The Connection

The grounded reasoning research (see findings.org) establishes that AI
reasoning without execution feedback is fundamentally limited beyond a
"deterministic horizon." TDD is the most practical grounding mechanism
because each test execution provides a binary signal: the AI's
understanding matches reality, or it does not.

Property-First Test Design strengthens this grounding by ensuring the
test measures the /right/ properties. A test that passes but checks the
wrong property provides a false grounding signal -- the AI thinks its
understanding is confirmed, but the confirmation is vacuous.

** 5.2 The Risk of Unintentional Tests

When an AI (or a human) writes a test without first enumerating which
properties to validate, three failure modes emerge:

1. *Over-assertion*: The test checks implementation details (structure
   sensitivity in Beck's desiderata). Changes to internals break the
   test even though behavior is unchanged. The test becomes noise.

2. *Under-assertion*: The test checks only that the code runs without
   error. A status-code-only test when value correctness is what
   matters. The test provides false confidence.

3. *Mis-assertion*: The test checks a property that is coincidentally
   true but not causally related to correctness. Refactoring breaks
   the test for the wrong reason, and the actual invariant goes
   unchecked.

Property enumeration before test writing directly addresses all three.

** 5.3 The Workflow

For AI-assisted development with grounding:

1. *Enumerate*: AI and human agree on which properties to validate.
   This is a design conversation, not a coding task.
2. *Prioritize*: Assign enforcement levels (P0 now, P1 next sprint,
   P2 when a bug demands it).
3. *Write*: AI writes the test, constrained to the enumerated
   properties. The property list prevents both over- and
   under-assertion.
4. *Execute*: Run the test. The result grounds the AI's reasoning
   against reality.
5. *Tighten*: When a bug escapes, identify the missing property,
   add it to the manifest, write the assertion.

** 5.4 Property Manifest as Specification

The property manifest (Section 3.4) serves triple duty:

- *For the human*: It is the acceptance criteria. "These are the
  properties I care about."
- *For the AI*: It is the constraint on test generation. "Check
  these properties, no more, no fewer."
- *For the codebase*: It is a living specification. The manifest
  evolves as understanding deepens.
