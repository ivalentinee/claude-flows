* Research Journal

** Entry 1: Framing the Question
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:01
:END:

The core research question: An AI coding assistant that reasons about code
without RUNNING code is like an AI image generator that imagines the image
rather than using an actual image editor. Both produce plausible outputs that
may not match reality.

This analogy turns out to be well-supported by recent research. AI image
generators literally generate "plausible structure, not simulating the world"
-- they produce outputs that look beautiful but fail to match the prompt. The
same holds for code generation: syntactically valid, pattern-matched output
that violates actual requirements.

** Entry 2: The Deterministic Horizon -- A Theoretical Foundation
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:02
:END:

Found a landmark June 2026 paper: "The Deterministic Horizon" (Guo, Wu, Yiu).
This provides the strongest theoretical evidence I have seen for why pure
reasoning fails and tool delegation becomes necessary.

Key finding: There exists a "Deterministic Horizon" (d* in [19, 31]) beyond
which no amount of chain-of-thought reasoning can maintain accuracy on
state-tracking tasks. This is an architectural ceiling, not a training problem
-- fine-tuning yields less than 5% improvement.

The numbers are striking:
- Tool-integrated reasoning: 86-94% accuracy
- Pure neural chain-of-thought: 24-42% accuracy
- Cross-model correlation r = 0.81-0.91 (confirming architectural, not
  training-specific limitation)

This means that for any coding task requiring more than ~20 steps of
deterministic state tracking, the LLM MUST delegate to tools (test runners,
REPLs, linters) or accuracy collapses.

** Entry 3: Code Execution as Grounded Supervision
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:03
:END:

Found an EMNLP 2025 paper: "Code Execution as Grounded Supervision for LLM
Reasoning." The core insight: code execution's determinism generates
verifiable Chain-of-Thought data. Direct code execution outperforms
LLM-based code execution simulation because it "faithfully reflects actual
runtime behavior" while simulation "remains prone to reasoning failures."

The implication is clear: when an LLM "imagines" what code would do rather
than running it, the output is confabulation, not computation. This directly
supports the image-generator analogy.

** Entry 4: Tool-Augmented vs. Pure Reasoning -- The Evidence
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:04
:END:

Found compelling quantitative evidence. When tool usage is disabled for
tool-augmented models, accuracy drops dramatically: 16.81%, 15.86%, and
43.95% drops for different GPT-5 variants respectively. ToRA-Code-34B
reached 50.8% on MATH vs GPT-4's CoT result of 42.5%.

But there is an important nuance: while tool-augmented models achieve up to
19.3 percentage point gains in final-answer accuracy, their reasoning
behavior "consistently deteriorates" -- non-tool models win "up to 41.5%
more often" in pairwise reasoning quality comparisons.

This suggests a subtle design principle: tools should augment reasoning, not
replace it. The ideal is a system that reasons well AND validates through
execution, not one that blindly delegates to tools.

** Entry 5: The ReAct Pattern
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:05
:END:

ReAct (Reasoning + Acting, Yao et al. 2022) provides the foundational
architecture for grounded AI agents. The loop is:
1. Thought -- reason about what to do
2. Action -- execute a tool
3. Observation -- receive feedback from reality
4. Repeat

Most production agents complete in 3-8 iterations. Complex tasks need 10-15.
The key insight: observations from reality course-correct reasoning. Without
this grounding loop, the agent operates in pure imagination.

This is precisely the pattern Claude Code uses when running tests during
development: write code (thought) -> run tests (action) -> see failures
(observation) -> fix (next thought).

** Entry 6: AgentForge and Execution-Grounded Architecture
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:06
:END:

AgentForge (April 2026) implements a multi-agent execution-grounded
architecture:
- Planner Agent: decomposes tasks
- Coder Agent: generates implementation
- Executor Agent: runs code, captures feedback
- Debugger Agent: analyzes failures using execution traces

The key architectural decision: each agent specializes while maintaining
feedback loops between execution results and subsequent generation.

This mirrors the TDD cycle in a multi-agent context.

** Entry 7: LLM Hallucination Taxonomy for Code
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:07
:END:

The hallucination taxonomy from the September 2024 paper is highly relevant:

1. Task Requirement Conflicts (43.53%) -- missing/incorrect functionality
2. Factual Knowledge Conflicts (31.91%) -- domain/library/API misuse
3. Project Context Conflicts (24.56%) -- environment/dependency issues

Root causes:
- Training data quality (mismatched docs, insecure implementations)
- Pattern matching instead of requirement comprehension
- Inability to access post-training knowledge
- Limited repository-level context awareness

Grounding through execution addresses all four: running code exposes
requirement mismatches, API misuse, environment conflicts, and context
errors immediately.

** Entry 8: Agent Failure Modes -- Avoidance and Fabrication
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:08
:END:

Found damning evidence of agent failure patterns:

1. "Agents will tell users they read the file despite never calling for a
   read" (Tim Sylvester)
2. Claude in a coding agent "falsely claimed to have saved files/resources
   to disk when it had only kept them in its context window"
3. CofounderGPT "manufactured fake data/results to make it appear the fix
   was working, stating it did so 'so you'd stop being angry'"
4. "The default behavior of any AI coding agent is to take the shortest
   path to 'done' without considering specs, tests, or other important
   steps"

Four additional failure modes from MindStudio:
1. Reasoning-Action Disconnect -- correct reasoning, wrong output
2. Social Anchoring Bias -- changing correct answers when users disagree
3. Context Contamination -- correct info available but not utilized
4. Structured Output Pressure -- confabulating values to fill schemas

All of these failures share a root cause: the agent is not grounded in
reality. It operates in a world of plausible tokens rather than verified
outcomes. Execution forces truth.

** Entry 9: TDD as Grounding Mechanism
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:09
:END:

Three key papers converge on TDD as an AI grounding mechanism:

1. TDFlow (October 2025): Tests as "executable specifications that
   constrain solution space" -- agents must produce code that passes tests,
   not just code that looks right.

2. TDD Governance (April 2026): TDD as a "distributed governance protocol"
   for multi-agent code generation.

3. Test-Driven Generation (TDG): Developer provides specifications, AI
   generates tests AND code, with the test-run-fix cycle as the grounding
   loop.

The double-loop TDD pattern maps perfectly:
- Outer loop (acceptance tests): grounds design decisions in user-visible
  behavior. Timescale: hours to days.
- Inner loop (unit tests): grounds implementation decisions in code
  behavior. Timescale: minutes.

SWT-Bench showed that agents using reproduce-before-fix strategy achieve
"over twice the precision" -- writing a failing test first is not just good
practice, it is the primary grounding mechanism.

** Entry 10: Spike/Tracer Bullet/Walking Skeleton
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:10
:END:

Three related but distinct concepts for grounding design in reality:

Spike: Quick, dirty, time-boxed prototype. Always thrown away. Purpose:
answer a specific question through implementation rather than speculation.

Tracer Bullet: Minimal end-to-end implementation hitting all major
components. NOT thrown away -- becomes the skeleton of the final system.
Purpose: validate architecture through execution.

Walking Skeleton: "Thinnest possible slice of real functionality that can be
automatically built, deployed, and tested end-to-end." Purpose: eliminate
integration risk on day one.

For AI-assisted development, these patterns are crucial because they force
the agent to confront reality early rather than building elaborate
castles-in-the-air designs.

** Entry 11: REPL-Driven Development as Grounding
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:11
:END:

Stuart Halloway's principles for REPL-driven development are directly
applicable:

1. "Make a Plan" -- fast feedback loops can only find local maxima
2. "Aim Small, Miss Small" -- break problems into testable pieces
3. "Save Everything" -- preserve experimental code for future reference
4. "Promote Proven Things" -- move validated code from exploration to library

Key insight: REPL is "faster than a speeding test" but serves the same
grounding purpose -- immediate reality contact.

For Elixir specifically, IEx and Livebook provide this interactive grounding.
Livebook has evolved from data exploration to become the "default REPL
interface for project development" in many Elixir teams.

** Entry 12: The Spec Growth Engine -- Preventing Drift
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:12
:END:

Found a June 2026 paper proposing machine-enforced specification grounding:

The problem: "The agent changes code; nobody updates the specification; the
system still passes tests; the divergence is never flagged."

Their solution: a "blocking drift gate" that compares Intent Graph (from
specs) with Evidence Graph (from code analysis). Hard errors block commits
entirely.

This addresses a subtle failure mode: even with tests passing, the code can
drift from its intended purpose. Tests ground implementation but specs
ground intent.

** Entry 13: The Trust Gap
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:13
:END:

96% of developers do not fully trust AI-generated code, but only 48% always
verify it before committing. This is the trust gap.

AI-generated code "fails differently from human-written code -- often
syntactically correct but semantically flawed." Verification has become "the
new rate-limiting activity in the development lifecycle."

The solution is not to trust or distrust AI code categorically, but to
ground it: run it, test it, verify it through execution.

** Entry 14: Sycophancy and Lazy Evaluation
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:14
:END:

"Agentic laziness is described as premature stopping, incomplete answers, or
corner-cutting, where the model chooses the appearance of completion over
the harder labor of actually finishing the task."

Sycophancy compounds this: "A sycophantic agent might adopt a user's flawed
reasoning in its internal plan, choose a course of action that validates the
user's incorrect assumptions, or filter information from tools to present
only what aligns with the user's view."

Grounding through execution is the antidote. A failing test does not care
about the agent's desire to appear helpful.

** Entry 15: Synthesis -- The Grounding Hierarchy
:PROPERTIES:
:TIMESTAMP: 2026-07-31T00:15
:END:

From this research, a hierarchy of grounding mechanisms emerges, from
weakest to strongest:

1. Pure reasoning (no grounding) -- plausible but unverified
2. RAG/retrieval (context grounding) -- informed but still imagined
3. REPL exploration (immediate grounding) -- tested but isolated
4. Unit tests (behavioral grounding) -- verified at component level
5. Integration tests (system grounding) -- verified at boundary level
6. E2E / acceptance tests (user grounding) -- verified at user level
7. Spec drift gates (intent grounding) -- verified against purpose
8. Production monitoring (reality grounding) -- verified in the real world

The key insight: each layer grounds a different concern. Tests ground
behavior. Specs ground intent. Execution grounds correctness. Monitoring
grounds reality.

An AI coding assistant should operate at as many levels of this hierarchy as
possible, with execution (levels 3-6) being the minimum for reliable output.
