* Grepability Experiment Log
** Methodology
All searches performed using file-glob and content-grep tools (equivalent to
=find= and =grep -B10 -A10= / =grep -rn=). Each grep invocation counts as one
"hop". Dead ends are hops that did not advance understanding of the data flow.

* Experiment 1: Trace =maxHeight= Through the System
** Starting Question
"Where does =maxHeight= originate, how does it travel through the system, and
where does it get consumed?"

** Hop Log

| Hop | Target                                          | Result                                                    | Advance? |
|-----+-------------------------------------------------+-----------------------------------------------------------+----------|
|   1 | =grep -rn maxHeight= (all files)                | 46 files. Overwhelming. No clear origin/sink.             | Partial  |
|   2 | =grep maxHeight= in =types/templateRun/request.ts= | Found =maxHeight?: MaximumHeight= -- name CHANGES to type alias | Yes      |
|   3 | =grep MaximumHeight= in same file               | =MaximumHeight= is just =number=. Type alias adds nothing | Dead end |
|   4 | =grep maxHeight= in =compiler/buildRun.ts=      | =maxHeight= goes into =maxHeightToScalingFactor()= -- NAME CHANGES to =scalingFactor= | Yes |
|   5 | =grep= in =compiler/maxHeightToScalingFactor.ts= | Conversion logic found. =maxHeight= -> =scalingFactor= completely | Yes      |
|   6 | =grep scalingFactor= in =graphics/server/operations/runtimeDetails.ts= | =scalingFactor= becomes string ='scaling factor'= (with space) in an array | Yes |
|   7 | =grep scalingFactor|scaling_factor= in =template_runner/= | 26 files. Mixed TS/Elixir. Hard to see the flow          | Partial  |
|   8 | =grep= in =template_runner/lib/=                 | Found =merge_runtime_scaling_factor= extracting from =extra["scalingFactor"]= | Yes |
|   9 | =grep max-height= in =compiler/standalone.ts=   | CLI arg =--max-height= -> =maxHeightArg= -> =maxHeight= -> =buildRun()= | Yes |
|  10 | =grep scalingFactor= in =graphics/server/operations/processImageOutput.ts= | No matches. Dead end -- name not present in this consumer | Dead end |

** Results
- Hops: 10
- Dead ends: 2 (hops 3 and 10)
- Trace complete: YES, but only for the server-side path

** Name Transformations Found (the core grepability problem)
The value undergoes FIVE name changes across the system:

| Boundary          | Name Before                     | Name After                    |
|-------------------+---------------------------------+-------------------------------|
| Type definition   | =maxHeight=                     | =MaximumHeight= (type alias) |
| Compiler          | =maxHeight=                     | =scalingFactor= (computed)    |
| Runtime details   | =scalingFactor= (property)      | ='scaling factor'= (string)   |
| Elixir boundary   | =scalingFactor= (camelCase)     | =scaling_factor= (snake_case) |
| CLI boundary      | =maxHeight= (JS)                | =--max-height= (CLI arg)     |

** What "3-hop success" would look like
1. A consistent name like =outputScalingMaxHeight= used from API to compiler
2. The computed value named =scalingFactorFromMaxHeight= instead of just =scalingFactor=
3. A comment at the =maxHeightToScalingFactor= call site: "// maxHeight -> scalingFactor: this is the only conversion point"

* Experiment 2: Trace =scalingFactor= Through Elixir
** Starting Question
"How does =scalingFactor= enter the Elixir template_runner and where does it get
used?"

** Hop Log

| Hop | Target                                          | Result                                                         | Advance? |
|-----+-------------------------------------------------+----------------------------------------------------------------+----------|
|   1 | =grep scalingFactor|scaling_factor= in =template_runner/lib/= | Only 1 file: =setup.ex=. Where does it come FROM?             | Partial  |
|   2 | =grep= broadly in =template_runner/=            | 26 files (many are dist/). Noise from compiled bundles        | Partial  |
|   3 | =grep extra= in =setup.ex=                      | =scalingFactor= comes from =data.template_run.extra=. What is =extra=? | Yes |
|   4 | =grep defstruct= in =template_runner/lib/=      | Found =Runner= struct has =:template_run= field. No =extra= visible | Partial  |
|   5 | =grep extra= in =template_run.ex=               | =field(:extra, :map)=. It is a schemaless map! Black hole for grep. | Yes |
|   6 | =grep run_options= in =template_run.ex=         | =field(:run_options, :map, source: :runOptions)=. Another opaque map. | Yes |
|   7 | Read =compiler.ex= directly                     | =max_height = get_in(template_run.run_options, ["templateRunOptions", "maxHeight"])= | Yes |

** Results
- Hops: 7
- Dead ends: 0 outright, but hops 1-2 were low-value
- Trace complete: YES

** Key Anti-Patterns Found

*** 1. Opaque =:map= fields as data transport
=template_run.extra= is typed as =:map= in the Ecto schema. This means:
- You cannot grep for what keys exist in =extra=
- The only way to discover =extra["scalingFactor"]= is to grep for the string literal ="scalingFactor"=
- If someone renames the key in TypeScript, the Elixir code breaks silently

*** 2. Cross-language boundary with no contract
The =extra= map is populated in TypeScript (=buildRun.ts=), serialized to JSON, stored in
PostgreSQL, and read in Elixir (=setup.ex=). The shape of =extra= is:
- NOT defined in a shared schema
- NOT validated at the boundary
- Only discoverable by reading BOTH codebases

*** 3. Double indirection through =run_options=
=maxHeight= lives at =run_options["templateRunOptions"]["maxHeight"]=:
- Elixir field name: =run_options= (snake_case)
- JSON source column: =runOptions= (camelCase, via =source: :runOptions=)
- Nested key: ="templateRunOptions"= (camelCase string)
- Final key: ="maxHeight"= (camelCase string)

To trace this, you need to know ALL FOUR naming conventions simultaneously.

** What "3-hop success" would look like
1. A typed struct =TemplateRunExtra= with explicit fields =:scaling_factor=, =:dimensions=
2. A YAML/protobuf schema shared between TS and Elixir defining the =extra= shape
3. A module-level @moduledoc in =setup.ex= listing all fields read from =extra=

* Experiment 3: Find What File Handles "Operation Result Processing"
** Starting Question
"Which file processes the results of an operation execution?"

** Hop Log (filename search first, then grep)

| Hop     | Target                                                       | Result                                                | Advance? |
|---------+--------------------------------------------------------------+-------------------------------------------------------+----------|
| find 1  | =src/**/*result*= (case insensitive)                        | 17 files. =resultPublisher=, =resultWaiter=, =getResult= -- none say "operation result" | No  |
| find 2  | =src/**/*operation*result*=                                  | 0 files. Complete miss.                               | Dead end |
| find 3  | =src/**/*process*=                                           | 5 files. =processImageOutput=, =runInSubprocess= -- not it | No       |
| grep 1  | =operation.?result|process.*operation|operationResult=       | 10 files. =operationProcessor.ts= looks promising     | Yes      |
| grep 2  | Content of =operationProcessor.ts=                           | Preprocessing only (=pre=), no result handling (no =post=)| Partial  |
| grep 3  | Content of =runOperation.ts=                                 | FOUND: =operation.fn()= call and =processedResult= handling | Yes      |
| grep 4  | Content of =runOperationWrapper.ts=                          | Wrapper that calls =runOperation= and handles errors  | Yes      |

** Results
- Filename searches: 3 (all failed or were unhelpful)
- Grep hops: 4
- Total: 7
- Dead ends: 3 (all filename-based)

** Key Anti-Patterns Found

*** 1. The actual file is named generically
The file that processes operation results is =platform/generic/fromServices/api/run/runOperation.ts=.
- "runOperation" does not suggest "result processing"
- It is buried 5 directories deep in a generic path
- =platform/generic/fromServices/api/run/= is a path where every segment is generic

*** 2. No dedicated result-processing file exists
Operation result processing happens INLINE in =runOperation.ts= (lines 46-62).
There is no =processOperationResult= function or file. The result handling is:
#+begin_src typescript
const result = await operation.fn(operationServices, { scalingFactor, ...config }, processedArgs, operationData);
const processedResult = operationProcessor.post ? await operationProcessor.post(operation, result) : result;
#+end_src
The result is processed inline with no named intermediate step.

*** 3. =operationProcessor.ts= is a misleading name
This file only handles PREprocessing (converting between buffer/file formats).
The actual operation processing (running + result handling) is in =runOperation.ts=.

** What "3-hop success" would look like
1. A file named =operationResultProcessor.ts= or a clearly named function =processOperationResult=
2. The =runOperation.ts= file split into =executeOperation.ts= + =processOperationResult.ts=
3. At minimum: a comment at the top of =runOperation.ts= saying "This file executes operations and processes their results"

* Anti-Pattern Catalog
** 1. Value Renames at Boundaries (most damaging)

| Value          | Names It Takes                                                              | Files Involved                            |
|----------------+-----------------------------------------------------------------------------+-------------------------------------------|
| maxHeight      | =maxHeight=, =MaximumHeight=, =max_height=, =--max-height=, =maxHeight= (string key) | request.ts, buildRun.ts, standalone.ts, compiler.ex |
| scalingFactor  | =scalingFactor=, =scaling_factor=, ='scaling factor'= (string with space)   | buildRun.ts, setup.ex, runtimeDetails.ts  |
| run options    | =runOptions=, =run_options=, =templateRunOptions= (nested), =RunOptions=    | getRunData.ts, template_run.ex            |

*Impact*: A grep for =maxHeight= will NOT find where the value is consumed as
=scalingFactor=. The conversion happens silently in =maxHeightToScalingFactor.ts=.
Someone debugging "why is my maxHeight not working?" must know this function exists
to cross the boundary.

** 2. Generic Containers / Opaque Maps

| Container            | Location                     | What It Hides                                    |
|----------------------+------------------------------+--------------------------------------------------|
| =extra: :map=        | =template_run.ex= field      | =scalingFactor=, =dimensions=, =progress=, =operationData= |
| =run_options: :map=  | =template_run.ex= field      | =templateRunOptions.maxHeight=, =destination=, =priority= |
| =config= object      | =runOperation.ts= parameter  | =quality=, =outputs=, =scalingFactor= (spread in) |
| =request= object     | =getRunData/entries.ts=       | typed as ={[key: string]: unknown}=               |

*Impact*: =get_in(extra || %{}, ["scalingFactor"])= is the only way to discover
that =extra= contains =scalingFactor=. The Ecto schema says =field(:extra, :map)= --
there is no type information. Grep for =scalingFactor= works, but grep for
"what fields does extra contain?" is impossible.

** 3. Generic / Unhelpful Names

| Name                                          | Why It Is Unhelpful                                       |
|-----------------------------------------------+-----------------------------------------------------------|
| =platform/generic/fromServices/api/run/=      | Every path segment is generic. 5 levels of meaninglessness |
| =operationProcessor.ts=                       | Sounds like it processes operations; actually only preprocesses args |
| =entries.ts=                                  | Generic name for "validation functions for run request fields" |
| =getRunData.ts=                               | "Run data" is vague -- it validates and transforms the request |
| =setup.ex=                                    | Generic name for "resolve operation arguments and merge config" |
| =runtimeDetails.ts=                           | Converts typed config into untyped name/value pair arrays |
| =MaximumHeight= (type alias)                  | Alias for =number= that adds no information              |

** 4. Missing Intermediate Variables / Inline Data Passing

| Location                          | What Happens                                                 |
|-----------------------------------+--------------------------------------------------------------|
| =runOperation.ts= line 46        | =scalingFactor= spread into config inline: ={ scalingFactor, ...config }= |
| =setup.ex= line 38               | Result of =merge_runtime_scaling_factor= passed directly into map literal |
| =buildRun.ts= line 23            | =scalingFactor= and =dimensions= destructured then immediately packed into =extra= |
| =getRunData.ts= line 74          | =maxHeight= nested inside =templateRunOptions= inside =runOptions= inline |

*Impact*: When data is passed inline, there is no named binding to grep for.
The expression ={ scalingFactor, ...config }= means =scalingFactor= disappears
into the =config= object. A grep for =scalingFactor= in downstream consumers
finds =config.scalingFactor= -- but nothing connects that back to =buildRun.ts=.

** 5. Cross-Language Boundary Without Shared Schema

| Boundary                        | TS Side                        | Elixir Side                           | Shared Contract |
|---------------------------------+--------------------------------+---------------------------------------+-----------------|
| =extra= map                    | =buildRun.ts= (populates)     | =setup.ex= (reads)                   | NONE            |
| =run_options= / =runOptions=   | =getRunData.ts= (populates)   | =compiler.ex= (reads)                | NONE            |
| compiled template output        | =standalone.ts= (writes JSON) | =compiler.ex= (reads JSON)           | NONE            |
| CLI arguments                   | =standalone.ts= (=--max-height=) | =compiler.ex= (passes =--max-height=) | Implicit only   |

*Impact*: Renaming a key in TypeScript silently breaks Elixir. There is no
compile-time or schema-validation check. The only way to verify compatibility
is to read both codebases and manually match string keys.

** 6. String-Keyed Access Patterns

Examples of accessing data via string keys rather than typed fields:
- =get_in(template_run.run_options, ["templateRunOptions", "maxHeight"])=
- =get_in(extra || %{}, ["scalingFactor"])=
- =request["config"]=, =request["callId"]=, =request["operationName"]=
- =parsed["compiledTemplate"]=, =parsed["extra"]=

*Impact*: String-keyed access is invisible to static analysis and refactoring
tools. Renaming =maxHeight= to =maxOutputHeight= in TypeScript requires a
manual search through Elixir code for the string ="maxHeight"=.

The most damaging anti-pattern is *value renames at boundaries*: a single
concept (=maxHeight=) takes 5 different names across the system, and each
rename breaks the grep chain. The second most damaging is *opaque map
containers*: the =extra= and =run_options= fields are typed as =:map= with no
discoverable schema, making it impossible to know what they contain without
reading every access site.
