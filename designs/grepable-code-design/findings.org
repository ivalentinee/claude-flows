* Grepable Code: Research Findings

** 1. The "Grepable Code" Concept

*** Definition

Grepable code is code structured so that its behavior, data flow, and
architecture are discoverable using only ~find~ (filenames) and
~grep -B10 -A10~ (local context), without needing to read entire
modules or trace multi-file call chains.

The concept is well-known in the programming community (Hillel Wayne
called it "an underrated code quality"), though much of the writing
about it exists in blog posts, newsletters, and Hacker News
discussions rather than in formal literature.

*** Why It Matters

- *10x discovery gap*: matklad observes that finding /where/ to make
  changes takes 10x longer than making them. Grepability directly
  attacks this.
- *IDE independence*: grep works in any environment -- terminals,
  CI logs, code review tools, unfamiliar codebases. IDE-dependent
  navigation (go-to-definition, find-references) requires setup and
  language-server support.
- *Scales with codebase size*: unlike reading comprehension (which
  degrades as codebases grow), grep performance is roughly O(n) in
  file count and can be made fast with tools like ripgrep.
- *Works for non-authors*: the person grepping is almost never the
  person who wrote the code. Grepability is a form of empathy for
  future readers.
- *AI tool compatibility*: LLM-based coding assistants (Claude Code,
  Copilot, Cursor) use the same ~grep~ and ~find~ primitives. Code
  that is grepable for humans is also grepable for AI agents.

*** The Fundamental Principle

Every important concept, value, or behavior in the codebase should
have a "grep handle" -- a unique, stable string that connects its
definition to all its usage sites. When you grep for that handle, you
find:
1. Where it is defined
2. Where it is used
3. Where it crosses boundaries
4. Where it is transformed

If any of these sites use a /different/ name for the same concept, the
grep trail breaks.

** 2. Naming for Discoverability

*** Principles That Make Code Grep-Friendly

**** 2.1 Unique names (avoid collisions)
Each important entity should have a name that produces a manageable
number of grep results. The name should be specific enough that
grepping for it does not drown in false positives.

| Anti-pattern         | Grep-friendly alternative |
|----------------------+---------------------------|
| ~data~               | ~templateData~            |
| ~config~             | ~renderConfig~            |
| ~handler~            | ~messageQueueHandler~     |
| ~result~             | ~compilationResult~       |
| ~process~            | ~processRenderJob~        |
| ~item~               | ~graphNode~               |
| ~value~              | ~parameterValue~          |
| ~type~               | ~nodeType~                |

**** 2.2 Consistent names (no renaming at boundaries)
The same concept should use the same name everywhere it appears. When
a value crosses a boundary (API -> backend -> database), its core name
should remain recognizable.

#+begin_example
# BAD: concept changes name at each boundary
Frontend:  templateId
API body:  graph_id
Backend:   documentRef
Database:  doc_id

# GOOD: concept keeps its core name, only case convention changes
Frontend:  templateId
API body:  template_id
Backend:   templateId
Database:  template_id
#+end_example

When case convention must change (camelCase -> snake_case), the /root
words/ should remain identical so that a case-insensitive grep (~grep
-i templateid~) finds all occurrences.

**** 2.3 Explicit names (no generic containers)
Names should reveal what data flows through them. Generic container
names (~data~, ~payload~, ~extra~, ~options~, ~params~, ~context~,
~info~, ~meta~) are grep-hostile because they match everything and
reveal nothing.

The test: if you can replace the name with ~stuff~ and nothing
changes, the name is too generic.

**** 2.4 Domain-specific names (ubiquitous language)
From DDD (Fowler/Evans): use the same term that domain experts use.
This creates a single vocabulary that spans conversations,
documentation, and code. It also makes grep more powerful because the
search term is the same one humans use when discussing the system.

**** 2.5 No abbreviations (spell it out)
Abbreviations break grep when different developers abbreviate
differently (~tpl~ vs ~tmpl~ vs ~template~, ~cfg~ vs ~conf~ vs
~config~). Spell out names in full. The only acceptable abbreviations
are universally understood ones (~id~, ~url~, ~http~).

**** 2.6 Semantic suffixes/prefixes (Elixir convention)
Elixir demonstrates how naming conventions can encode behavior:
- ~!~ suffix: function raises on error
- ~?~ suffix: function returns boolean
- ~is_~ prefix: guard-clause-compatible type check
- ~size~ vs ~length~: O(1) vs O(n) computation

These are greppable because they're syntactic patterns. You can grep
for ~def.*!~ to find all raising functions.

*** Anti-Patterns That Break Grepability

**** Single-letter variables
~x~, ~y~, ~n~, ~e~ -- impossible to grep for. Only acceptable in
very tight scopes (lambda parameters, loop indices) where the
~-B10 -A10~ context window is sufficient.

**** Dynamically constructed names
#+begin_src javascript
// UNGREPABLE: function name is assembled at runtime
const action = 'handle' + eventType.charAt(0).toUpperCase() + eventType.slice(1);
this[action]();

// GREPABLE: explicit dispatch
switch (eventType) {
  case 'click': this.handleClick(); break;
  case 'submit': this.handleSubmit(); break;
}
#+end_src

**** Compact destructuring aliases (Elixir example from Ionov)
#+begin_src elixir
# UNGREPABLE: compact alias hides full module path
alias SomeProject.Family.{Son1, Son2}

# GREPABLE: each alias is a complete, searchable string
alias SomeProject.Family.Son1
alias SomeProject.Family.Son2
#+end_src

**** Re-exports and barrel files
#+begin_src javascript
// UNGREPABLE: re-export hides the actual module
// index.ts
export { compileTemplate } from './templateCompiler';
export { runTemplate } from './templateRunner';
// Consumer imports from index, grep for compileTemplate doesn't show templateCompiler.ts

// GREPABLE: import directly from the source module
import { compileTemplate } from './compiler/templateCompiler';
#+end_src

**** Method chaining with generic names
#+begin_src javascript
// UNGREPABLE: what does .process() do? Which one?
pipeline.load().validate().process().save();

// GREPABLE: explicit function names reveal behavior
loadTemplate(input);
validateTemplateGraph(template);
compileTemplateToJS(template);
saveCompiledOutput(compiled);
#+end_src

**** Operator overloading
Google's C++ style guide explicitly warns: "finding the call sites for
overloaded operators may require a search tool that's aware of C++
syntax, rather than, e.g., grep."

** 3. Anti-Patterns That Break Grepability (Data Flow)

*** 3.1 "Data Bags" / God Objects
A data bag is a generic object that accumulates fields over time:
~context~, ~state~, ~data~, ~options~, ~config~. These break
grepability because:
- Grepping for ~context~ matches every function that touches the bag
- You cannot trace a specific field's journey through the system
- Fields are added/removed without type safety
- The object becomes a "god object" that everything depends on

Solution: decompose into specific, named parameters or typed
interfaces where each field has a traceable name.

*** 3.2 Implicit Data Flow
Data that flows through the system without appearing in function
signatures:
- Global/module-level mutable state
- Thread-local storage
- Hidden side-channel communication (environment variables read deep
  in call chains)
- Event buses where the event type is a generic string

These are invisible to grep because the data's path leaves no textual
trace in the code.

*** 3.3 Value Renaming at Boundaries
When the same logical value gets a different name as it crosses a
module boundary:

#+begin_example
# API layer calls it "graphSpec"
# Compiler layer calls it "templateAST"
# Runner layer calls it "compiledProgram"

A developer grepping for "graphSpec" finds only the API layer.
They must /read/ the API code to discover it becomes "templateAST"
in the compiler, then read the compiler to find "compiledProgram".
Each rename adds a mandatory grep hop.
#+end_example

*** 3.4 Stringly-Typed Dispatch
#+begin_src javascript
// UNGREPABLE: the string "render" connects caller to handler
// but grep for "render" matches hundreds of lines
eventBus.emit('render', data);
eventBus.on('render', handler);

// GREPABLE: use a unique constant name
const TEMPLATE_RENDER_REQUESTED = 'template:render:requested';
eventBus.emit(TEMPLATE_RENDER_REQUESTED, data);
eventBus.on(TEMPLATE_RENDER_REQUESTED, handler);
#+end_src

*** 3.5 Over-Abstraction (Metz's "Wrong Abstraction")
When code is over-abstracted, the abstraction layer becomes an opaque
wall. A developer must /read/ the abstraction to understand which code
path their case takes, rather than grepping for their specific use
case. Metz recommends "re-inlining" -- duplicating code to make each
use case explicit and separately greppable, then re-abstracting only
when a /true/ pattern emerges.

** 4. File Structure for Discoverability

*** 4.1 Screaming Architecture (Uncle Bob)
The top-level directory structure should reveal the system's purpose:

#+begin_example
# BAD: screams "this is Express/MVC"
controllers/
models/
views/
routes/
middleware/

# GOOD: screams "this is a template rendering system"
compiler/
templateRunner/
outputBuilder/
graphEditor/
#+end_example

*** 4.2 Feature-Based vs Layer-Based Organization
Layer-based (controllers/models/views) groups by technical role.
Feature-based groups by domain concept. Feature-based is more
greppable because ~find . -name '*template*'~ returns all
template-related files.

Hybrid approach (as used in Idunn): organize by domain at the top
level (~compiler/~, ~server/~, ~browser/~), then by feature within
each layer. This preserves both domain discoverability and layer
clarity.

*** 4.3 Filename as Grep Handle
A filename should be unique enough to serve as a grep handle. If you
have multiple files named ~index.ts~ or ~utils.ts~, ~find~ results are
noisy. Prefer filenames that encode their domain purpose:

| Anti-pattern  | Grep-friendly alternative     |
|---------------+-------------------------------|
| ~index.ts~    | ~templateCompiler.ts~         |
| ~utils.ts~    | ~graphValidation.ts~          |
| ~helpers.ts~  | ~nodeResolution.ts~           |
| ~types.ts~    | ~compilerTypes.ts~            |
| ~constants.ts~| ~renderDefaults.ts~           |

Note: ~index.ts~ is unavoidable in some module systems. The principle
is to minimize reliance on it as the /only/ meaningful file in a
directory, and to give directories themselves descriptive names.

*** 4.4 Directory Names as Domain Terms
Directory names should be domain terms that a developer would
naturally grep for:
- ~compiler/~ not ~core/~ or ~lib/~
- ~templateRunner/~ not ~runner/~ or ~executor/~
- ~outputBuilder/~ not ~builder/~ or ~factory/~

** 5. Cross-Boundary Naming Consistency

*** 5.1 The Ubiquitous Language Principle (DDD)
Evans and Fowler argue for a single, shared vocabulary between domain
experts and developers. This vocabulary should appear identically in:
- Conversations and documentation
- API contracts (request/response fields)
- Backend code (variables, function names)
- Database schema (column names)
- Frontend code (state, props)
- Log messages and error messages

When the vocabulary fractures (different teams use different terms for
the same concept), grep trails break at every boundary.

*** 5.2 Case Convention Bridges
When languages mandate different case conventions (JavaScript
camelCase, Elixir snake_case, PostgreSQL snake_case), the /root words/
should remain identical:

#+begin_example
JavaScript:  templateRunId
Elixir:      template_run_id
PostgreSQL:  template_run_id
API JSON:    templateRunId (or template_run_id, pick one and be consistent)
#+end_example

A case-insensitive grep (~grep -i 'templaterunid'~) should find all
occurrences across all layers.

*** 5.3 The Anti-Corruption Layer (DDD)
When integrating with external systems that use different terminology,
DDD recommends an "anti-corruption layer" that translates at the
boundary. The key for grepability: the translation should happen in
/one/ clearly-named location, and both the external name and internal
name should appear together at that translation point.

#+begin_src typescript
// Translation point: both names appear together, greppable
function fromExternalAPI(externalResponse: ExternalGraphSpec): TemplateGraph {
  return {
    templateId: externalResponse.graph_id, // external: graph_id -> internal: templateId
    nodes: externalResponse.elements.map(toInternalNode),
  };
}
#+end_src

*** 5.4 Log Messages as Grep Handles
Log messages should contain the same domain terms used in code:

#+begin_src typescript
// BAD: log message uses different term than code
logger.info('Processing document', { docRef: template.id });

// GOOD: log message uses same term as code
logger.info('Compiling template', { templateId: template.id });
#+end_src

This allows operators to grep logs using the same terms developers use
to grep code.

** 6. The 3-Hop Trace Test

*** Definition

The 3-hop trace test: for any value in the system, can you trace its
complete path (from origin to final use) in 3 or fewer grep hops?

A "hop" is one invocation of ~grep~ (or ~ripgrep~) that moves you
from one part of the codebase to another.

*** What Makes 3-Hop Tracing Possible

**** Hop 1: Find the origin
Grep for the value's name. You find its definition or entry point.
- Requires: a unique, consistent name
- Breaks when: the name is generic (~data~) or the value enters the
  system under a different name

**** Hop 2: Find the transformation
From the origin, grep for the function that processes this value. You
find where it's transformed or passed along.
- Requires: the function name reveals what data flows through it
- Breaks when: the function is generic (~process~, ~handle~) or the
  value is renamed when passed to the next function

**** Hop 3: Find the destination
From the transformation, grep for where the result lands. You find the
final consumer.
- Requires: the output maintains a recognizable name
- Breaks when: the result is stuffed into a generic container (~data~,
  ~result~, ~output~) or dispatched through an event bus

*** Concrete Example: Passing the Test

#+begin_example
Hop 1: grep "templateId"
  -> Found in src/server/http/controllers/templateController.ts:
     const { templateId } = req.params;
     const compiled = await compileTemplate(templateId);

Hop 2: grep "compileTemplate"
  -> Found in src/core/compiler/templateCompiler.ts:
     export async function compileTemplate(templateId: string): CompiledTemplate { ... }
     -> calls generateJavaScript(resolvedGraph)

Hop 3: grep "generateJavaScript"
  -> Found in src/core/compiler/jsBuilder/generateJavaScript.ts:
     export function generateJavaScript(graph: ResolvedGraph): string { ... }
  DONE: traced from HTTP request to JS output in 3 hops.
#+end_example

*** Concrete Example: Failing the Test

#+begin_example
Hop 1: grep "graph_id"
  -> Found in src/server/http/controllers/apiController.ts:
     const data = req.body;
     processRequest(data);

Hop 2: grep "processRequest"
  -> Found in src/server/services/requestProcessor.ts:
     function processRequest(data: any) {
       const result = transform(data);
       eventBus.emit('processed', result);
     }
  PROBLEM: "data" is generic, "transform" is generic,
  "result" is generic, event dispatch is stringly-typed.

Hop 3: grep "processed"
  -> 847 results. Which one handles our graph_id?
  FAILED: cannot trace the value.
#+end_example

*** The Checklist

To ensure a codebase passes the 3-hop trace test:

1. [ ] *Unique names*: every important entity has a name that produces
   <20 grep results in the codebase
2. [ ] *Consistent names*: the same concept uses the same root name
   across all boundaries (case convention may vary)
3. [ ] *Explicit function names*: function names reveal what domain
   data flows through them (~compileTemplate~, not ~process~)
4. [ ] *No generic containers*: data is passed in typed, named
   structures, not ~any~, ~object~, ~data~, or ~context~ bags
5. [ ] *No invisible dispatch*: event names, message types, and
   routing keys are unique constants, not generic strings
6. [ ] *Meaningful filenames*: ~find . -name '*template*'~ returns
   all template-related files
7. [ ] *Translation points are explicit*: where names must change
   (external API boundaries), both names appear together in one place
8. [ ] *Log messages use code terms*: grepping logs uses the same
   vocabulary as grepping code
