#+TITLE: Anti-Sycophancy Design Options
#+DATE: 2026-07-31

* Problem Statement

When an AI coding assistant agrees with a slightly-wrong user input, the error compounds
through conversation turns into confidently-wrong outputs. This is the "rough boar
syndrome" — named after a Russian internet phenomenon where ChatGPT built elaborate
constructs from small initial seeds of user error.

The problem has three layers:
1. *Single-turn sycophancy*: AI agrees with wrong statement in one response
2. *Multi-turn compounding*: Agreement in turn N becomes premise in turn N+1
3. *Architectural drift*: Compounded errors materialize as technical debt in code

* Design Space

The options below address different intervention points, from lightweight prompting
to structural workflow changes. They are not mutually exclusive — a final design
will likely combine elements from several options.

* Option A: Assertion Checkpoints

** Concept
At defined points in the conversation, the AI pauses to explicitly re-state its
understanding of the current technical context and checks it against the codebase.
This breaks the compounding chain by forcing reality checks.

** Mechanism
- After every N turns (or before implementation), AI generates a "current understanding" summary
- AI cross-references this understanding against actual code/architecture
- Discrepancies are flagged: "You said X, but the codebase shows Y"
- User must acknowledge discrepancies before AI proceeds

** Strengths
- Catches drift before it materializes in code
- Non-confrontational (checking understanding, not challenging user)
- Works within existing conversation flow
- Detectable: the AI can be instructed to do this in system prompts

** Weaknesses
- Adds conversational overhead
- Requires codebase reading at each checkpoint
- User may rubber-stamp checkpoints without reading
- Doesn't address single-turn sycophancy

** Implementation Complexity
Low — achievable through system prompt instructions and workflow conventions.

* Option B: Tiered Authority Model

** Concept
Define explicit categories for user requests with different AI deference levels.
The AI classifies each request and calibrates its pushback accordingly.

** Tiers
| Tier | Category | AI Behavior | Example |
|------+----------+-------------+---------|
| 1 | Preference/scope | Full deference | "Make button blue", "We don't need feature X" |
| 2 | Domain knowledge | Defer with curiosity | "Our users prefer mobile", "We use Postgres" |
| 3 | Implementation approach | Inform, then defer | "Use a cache here", "Add an index" |
| 4 | Architecture/safety | Challenge, require acknowledgment | "Skip auth for now", "Store in plaintext" |
| 5 | Factual error | Correct directly | "Elixir uses classes", "SQL injection isn't real" |

** Mechanism
- AI classifies incoming request into tier
- Tier determines response template:
  - Tier 1-2: Execute without questioning
  - Tier 3: "Before I implement this, I notice [existing code/pattern]. Want me to proceed anyway?"
  - Tier 4: "This would [consequence]. I recommend [alternative]. If you want to proceed anyway, confirm and I will."
  - Tier 5: "Actually, [correct information]. Shall I proceed with the corrected understanding?"

** Strengths
- Provides clear framework for when to push back
- Respects user authority where it's legitimate
- Challenges where it's genuinely needed
- Prevents both sycophancy and unwanted obstinance

** Weaknesses
- Classification is hard — many requests are ambiguous
- Wrong classification is worse than no classification (challenging preferences, deferring on safety)
- Adds cognitive overhead for the AI (meta-reasoning about tier before responding)
- May feel patronizing at higher tiers

** Implementation Complexity
Medium — requires careful prompt engineering and possibly examples for each tier.

* Option C: "Informed Consent" Protocol

** Concept
Borrowed from medical ethics: before implementing a request that has non-obvious
consequences, the AI ensures the user understands the tradeoffs. The AI never refuses,
but it ensures the user is making an *informed* decision rather than an uninformed one.

** Mechanism
For requests with potential consequences:
1. AI briefly states what the request will accomplish
2. AI states what side effects or tradeoffs exist
3. AI asks: "Want me to proceed?" (not "Are you sure?" — no judgment)
4. On confirmation, AI implements without further pushback

** Key Properties
- *Never refuses*: Respects user authority absolutely
- *Always informs*: Ensures user has the information to decide
- *Once only*: After informed confirmation, no further challenges on the same point
- *Non-judgmental*: States facts, not opinions ("This will X" not "You shouldn't X")

** Strengths
- Respects user autonomy fully
- Prevents uninformed errors without being paternalistic
- Natural — mirrors how good human engineers communicate
- No "challenge budget" problem — challenge is embedded in the inform step

** Weaknesses
- Requires good judgment about what needs informing (trivial requests shouldn't trigger it)
- Can slow down experienced users who already know the tradeoffs
- User may learn to skip/ignore inform steps (habituation)
- Doesn't catch compounding errors (each individual step may seem informed)

** Implementation Complexity
Low-Medium — can be implemented through system prompt conventions.

* Option D: Conversational Momentum Detection

** Concept
Explicitly detect when conversational momentum is building in a potentially wrong
direction. Flag it rather than just going along.

** Indicators of Dangerous Momentum
- User and AI have agreed on a premise that hasn't been verified against code
- User references AI's own previous output as evidence ("like you said...")
- Multiple turns have built on a single unverified assumption
- The conversation has drifted from stated goals
- Technical claims are being made without code references

** Mechanism
- AI maintains a mental model of "unverified premises" in the conversation
- When action is about to be taken on unverified premises, AI flags:
  "We've been building on the assumption that [X]. Let me verify this against the actual code before proceeding."
- After verification, either confirm and proceed, or flag discrepancy

** Strengths
- Directly targets the compounding problem
- Doesn't require classifying request types
- Catches the specific failure mode that creates "rough boar" situations
- Can be implemented as a periodic self-check

** Weaknesses
- Requires the AI to maintain meta-awareness of its own reasoning chain
- Hard to implement reliably — the AI may not notice its own drift
- May produce false positives (flagging verified premises)
- Adds latency

** Implementation Complexity
Medium-High — requires sophisticated prompt engineering or structural conversation mechanisms.

* Option E: Dual-Mode Operation

** Concept
Separate "implement" mode from "review" mode. In implement mode, the AI does what
the user asks. In review mode (triggered periodically or on-demand), the AI critically
examines what has been built.

** Mechanism
- *Implement mode*: Standard helpful assistant behavior. Execute requests, minimal pushback.
- *Review mode*: Triggered by user or automatically after N implementation steps.
  In review mode, the AI:
  - Re-reads the actual codebase (not its memory of it)
  - Compares what was built to what was intended
  - Identifies architectural inconsistencies
  - Flags potential technical debt
  - Reports discrepancies between user's stated goals and actual implementation
- After review, user decides what to fix and returns to implement mode

** Strengths
- Clean separation of concerns — no pushback fatigue during implementation
- Review catches compounding errors that individual-turn pushback misses
- Mirrors actual software development (implement + code review)
- User controls when review happens

** Weaknesses
- Errors compound during implement phase (by design)
- Review may come too late if much code has been written
- User may skip reviews ("I'll review later" → never)
- Two modes add complexity to the interaction

** Implementation Complexity
Medium — can be implemented through workflow conventions and explicit mode switching.

* Option F: Pre-Implementation Codebase Scan

** Concept
Before implementing any change, the AI automatically reads relevant existing code
to ground its response in reality rather than in the user's description.

** Mechanism
- User requests a change
- AI identifies which files/modules are affected
- AI reads those files BEFORE responding
- AI's response is grounded in actual code, not user's description of code
- If user's description doesn't match reality, AI notes the discrepancy

** Strengths
- Simple and effective
- Prevents the most common source of compounding errors (user's wrong mental model)
- Already partially implemented in Claude Code
- No confrontation — just grounding

** Weaknesses
- Adds latency to every interaction
- User may find it slow
- Doesn't help when the user's request is architecturally wrong but locally correct
- File selection is imperfect — may miss relevant context

** Implementation Complexity
Low — Claude Code already does this to some degree. Can be reinforced through
system prompt instructions.

* Option G: "State Your Objection, Then Comply" Protocol

** Concept
The AI always complies with user requests, but has a structured way to register
disagreement before complying. One sentence of objection, then full implementation.

** Mechanism
- If AI has a concern, format: "Note: [one-sentence concern]. Proceeding with your request:"
- Then implement fully, no hedging
- The concern is on record but doesn't block work
- User can choose to address it or ignore it

** Key Properties
- *Always complies*: No blocking, no repeated pushback
- *Always honest*: Concern is registered
- *Minimal friction*: One sentence, then work
- *Auditable*: Concerns are visible in conversation history

** Strengths
- Zero friction — user is never blocked
- Honest — concerns are stated
- Respects user authority
- Simple to implement
- No "challenge budget" problem — concern is noted once, then done

** Weaknesses
- One sentence may not convey the severity of serious issues
- User may learn to ignore the note lines (habituation)
- Doesn't prevent compounding (concern is noted but not resolved)
- Treats all concerns equally regardless of severity

** Implementation Complexity
Very low — achievable through a single system prompt instruction.

* Comparison Matrix

| Option | Addresses Compounding? | Respects Authority? | User Friction | Implementation Complexity |
|--------+------------------------+---------------------+---------------+---------------------------|
| A: Assertion Checkpoints | Yes (strong) | Yes | Medium | Low |
| B: Tiered Authority | Partially | Yes (structured) | Low-Medium | Medium |
| C: Informed Consent | Partially | Yes (fully) | Low | Low-Medium |
| D: Momentum Detection | Yes (strong) | Yes | Low | Medium-High |
| E: Dual-Mode | Yes (at review) | Yes | Low (between reviews) | Medium |
| F: Pre-Impl Scan | Yes (prevents) | Yes | Low | Low |
| G: State & Comply | No | Yes (fully) | Very Low | Very Low |

* Recommended Combinations

** Combination 1: "Grounded Informed Consent"
F (Pre-Implementation Scan) + C (Informed Consent) + G (State & Comply)

For each user request:
1. Read relevant code first (F)
2. If discrepancy between user's model and reality: inform and get acknowledgment (C)
3. If architectural concern but user's model is accurate: state concern, then comply (G)
4. If no concerns: implement directly

This is lightweight, respects authority, and catches the most common compounding trigger
(user's wrong mental model of the code).

** Combination 2: "Checkpoint + Review"
A (Assertion Checkpoints) + E (Dual-Mode)

For extended implementation sessions:
1. Implement freely between checkpoints
2. Every N turns, pause for assertion checkpoint (A)
3. After major implementation milestones, switch to review mode (E)
4. Use review findings to course-correct before continuing

This is more heavyweight but catches compounding even in long sessions.

** Combination 3: "Full Stack Anti-Sycophancy"
F (Pre-Impl Scan) + B (Tiered Authority) + D (Momentum Detection) + A (Checkpoints)

Maximum protection:
1. Ground every response in actual code (F)
2. Classify requests and calibrate pushback (B)
3. Monitor for conversational momentum toward wrong conclusions (D)
4. Periodically verify shared understanding (A)

This is the most robust but also the most complex and potentially annoying.
Only appropriate for high-stakes codebases.
